### Stripe create_customer hardening

Rewrote the function against three identified weaknesses.

- **Removed the `environment` input and the test/live conditional.** Client supplied environment selection was a key selection risk. Stripe test versus live mode is determined entirely by which secret key is used, so a single env var is sufficient. Post dev/prod split each workspace holds its own key value and the branch is unnecessary. Confirmed against Xano documentation via their support chat.
- **Added an Idempotency-Key header** derived from `users_id`, format `customer_create_{users_id}`. Protects the case where the Stripe call succeeds but the response is lost, so a later retry returns the original customer rather than creating a duplicate. Required adding `users_id` as a function input.
- **Reshaped the response** to return `{status, id}` rather than the raw api object, so callers can branch on status for error handling and retry.

Initial test returned a 400 from nginx due to a malformed header name (`Idempotency Key` with a space rather than a hyphen). Corrected to `Idempotency-Key`. Verified working by running the same call twice and confirming the same customer id returned both times.

### Reconciliation background task

Built `reconcile_stripe_customers` task to retry failed or missing customer creation outside the synchronous signup path.

- Queries `users` for rows with no `stripe_customer_id` and a retry count below the cap.
- Loops each row, calls `stripe_create_customer`, and on success writes the customer id, on failure increments `stripe_customer_retry_count` and sets `stripe_customer_last_attempt_at`.
- Retry cap of 5 prevents a permanently failing record looping indefinitely.
- Scheduled at 900 second frequency.

Two new fields added to `users`: `stripe_customer_retry_count` (int) and `stripe_customer_last_attempt_at` (timestamp).

First run reconciled 41 existing users successfully. Second run returned zero rows and correctly did not call the function.

Note: those 41 customers were created against the Stripe test key currently held in the env var. They are test mode customers, not live ones.

### Auth pre-request script

Built a collection level pre-request script (applied to both collections) that logs in and stores a fresh token only when the current one is missing or stale.

Initial implementation decoded the JWT `exp` claim to determine staleness. This failed, refreshing on every single request. Diagnosis confirmed the token payload decoded to null.

**Root cause: Xano issues JWE tokens, not plain JWS.** The token header shows `A256KW` and `A256CBC-HS512`, meaning the payload is encrypted and cannot be decoded client side at all. Expiry claim reading is impossible by design.

Reworked to a time based approach. On successful login the script stores both the token and a `bearerTokenExpiry` timestamp computed as now plus the known 3600 second TTL, then checks that stored timestamp rather than attempting to read the token. Note the TTL constant is coupled to the Xano `expiration` value and both must change together.

Verified working: cleared token, first send issued and stored a token, second send reused it with no refresh logged.

### instant_stories regression found and fixed

Attempted to create a story via `POST /instant_stories` to seed the checkout session test. Returned `ERROR_FATAL` with `Unable to locate auth: extras.active_profile_id`.

The endpoint was reading a flat `extras.active_profile_id`, which predates the change that made `active_profile` a nested object. The token correctly carries `extras.active_profile.id`. This is the known Xano behaviour where a missing path segment in `auth.extras` throws a hard fatal error rather than returning null.

Fixed by pointing the endpoint at the nested path. Also removed `user_profiles_id` as a request input, since profile context must come from token extras and not client supplied values. Retested and confirmed a 200 with a new story created.

This is the first regression the Postman suite has surfaced and it validates the approach. Xano test mode does not pass `auth.extras`, so this class of bug is invisible to the built in test runner and only appears under real token testing.

## Key learnings

- **Xano issues JWE not JWS tokens.** Encrypted payload, no client side decoding. Any token expiry or claim reading must use a stored value, not the token itself. This also means the React Native frontend cannot read profile context from the token and must source it from an endpoint and hold it in state.
- **Custom functions are not HTTP reachable in Xano**, so internal key gating applies only to actual exposed endpoints, not to the function layer beneath them.
- **Stripe test versus live is determined by the secret key alone.** No environment awareness or mapping is needed, the key is the selector.
- **Idempotency keys protect against lost responses, not just duplicate calls.** The failure mode is a success that never gets recorded, followed by a retry.
- **Endpoints hardened before the `active_profile` object change may still read the flat key.** Expect more of these to surface during A series assertion work.
