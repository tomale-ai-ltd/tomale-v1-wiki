## Decisions made

### user_profiles — soft-delete blocks currently-active profile
Parent must switch off the active profile before deleting it. Prevents broken-token state where JWT `active_profile.id` references a soft-deleted record. Enforced via precondition `$auth.extras.active_profile.id != $profile.id`. Failure returns 422 `CANNOT_DELETE_ACTIVE`.

### user_profiles — schema rename `is_default` → `is_primary`
Renamed at schema level and across POST, PATCH, GET, DELETE endpoints and select_profile fallout. Rationale: "default" was overloaded (permanent adult, signup-created, fallback landing profile). `is_primary` semantically cleaner and extends cleanly to future multi-adult support ("additional adults" not "non-default adults"). Confirms the household owner role for account-transfer / account-recovery semantics later.

### user_profiles — DELETE verb, soft-delete implementation
HTTP DELETE semantically expresses "remove from my view" to clients, cache layers, and future developers. Backend implementation is `db.edit` setting `deleted_at`. Separation of wire protocol from storage strategy is intentional and standard REST practice. Response 204 (or 200 empty in Xano's rendering — functionally equivalent).

### user_profiles — parental PIN gate deferred, tracked
Deferred to pre-launch hardening. Ship user_profiles group without PIN gate. Content moderation catches the actual content-safety risks; PIN adds durability/commercial protection on top. Full design captured — see decision note.

### user_alerts — role, scope, and CRUD split
`user_alerts` is the in-app inbox (persistent message centre). Not a mirror of push notifications; push is a separate transient delivery channel. Public API surface: READ (list + single) and UPDATE (mark_read + mark-all-read). No public create/delete. Alert creation happens internally via `create_user_alert()` custom function called by moderation, webhooks, and admin broadcast. Deletion is server-side maintenance (scheduled hard-delete of old read alerts).

### user_alerts — return all regardless of read status
GET all returns full history including read alerts. Unread count computed client-side from same response for the bell-icon badge — one call, no separate unread-count endpoint for V1.

### user_alerts — action_url on alerts (deep link)
Alerts carry an optional `action_url` (text, nullable) so the frontend can render a CTA button that opens the target resource. Chosen over typed entity_type + entity_id FK pattern for simplicity, versionability, and universal handling. Full design in decision note.

### Deep-link URL format — Option A (custom scheme now, Universal Links pre-launch)
Store `tomalerntest://` scheme URLs in `action_url` for V1 build. Migration to `https://tomale.ai/app/*` Universal Links + production `tomale://` scheme is a single pre-launch workstream. Existing rows continue working via fallback scheme handler.

### Push notifications — deferred to post-V1 fast-follow
Fully separable feature, no interweaving with existing backend/frontend. Additive schema (`user_push_tokens` table), one line in `create_user_alert` to fire push alongside inbox insert, isolated frontend permissions + settings work. Estimated ~2-3 focused days when scheduled. In-app inbox + email fallback covers critical delivery for V1.

## Issues encountered & resolved

- **PATCH 404 routing failure** — `user_profiles.id` is uuid, XanoScript input was declared `int`. Path parser failed to coerce uuid string to int, endpoint didn't match, 404 from Xano's routing layer. Fixed by changing input declaration to `uuid user_profiles_id`.
- **`regex_match` deprecated** — Xano deprecated `regex_match` in favour of `regex_matches` (returns boolean directly, no equality-comparison needed). Cleaner check pattern.
- **`$patch_data` dead code in PATCH** — leftover from earlier draft using variable-assembly pattern. Removed. Coalesce via `first_notempty` in the `db.edit` data block handles partial updates directly.
- **Avatar_key regex ran unconditionally** — validation was outside the `if ($input.avatar_key != null)` wrapper, causing name-only PATCH requests to 422 on the null avatar_key. Wrapped correctly.
- **`is_default` residual in select_profile** — auth/select_profile still referenced the old field name after the rename. Fixed. Full-codebase search for `is_default` completed.

## Learnings / principles reinforced

- **Xano PATCH endpoints benefit from optional inputs + coalescing.** Required inputs force the endpoint into PUT-like semantics; optional inputs + `first_notempty` fallback against a fetched record give true partial-update behaviour matching HTTP PATCH conventions.
- **HTTP verbs describe intent, not implementation.** DELETE endpoint doing soft-delete via db.edit is standard and correct. Verb serves the client contract; storage strategy serves the data model.
- **Path parameter types must match table id types.** uuid tables need `uuid` inputs. Silent 404 at routing layer is the failure mode; endpoint logic never runs.
- **Renames are cheapest when done at first divergence.** `is_default` → `is_primary` was one endpoint's cost today, would have been six-plus endpoints' cost in three months.
- **In-app inbox and push notifications serve different roles**, not either/or. Inbox = persistent record reaching 100% of active users. Push = transient re-engagement reaching only opted-in users (~51% iOS opt-in rate). Modern best practice uses both, coordinated. For V1, inbox + email fallback covers critical delivery.
- **Deep-link URL strings on alert rows beat typed FKs** for the alert-to-target mapping. One column, one convention, universal handling. Typed FKs would force switch statements in every alert generator and frontend.
- **Xano's Swagger export makes Postman collection maintenance essentially free** via OpenAPI import + merge mode. Same integration pattern as the frontend's existing `xano.yaml` sync.
