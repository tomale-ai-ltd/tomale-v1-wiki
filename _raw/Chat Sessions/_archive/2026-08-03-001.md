## Work completed

### Image pipeline diagnosis

An executor_runs export from an earlier story revealed several issues:

- **OpenAI API key stored in plaintext** in the executor_runs api_request column across many rows. The full request headers including the Authorization bearer were being logged.
- **Duplicate executor runs.** Jobs were being claimed by successive worker ticks and processed more than once. Root cause traced to leases being granted at claim time rather than at execution start.
- **Base64 image data stored in api_response**, causing catastrophic row bloat. A 28 row export was 72MB because every generated image was stored a second time as base64 in a log table.
- **Unreachable error branches** in executor_page_image. The branches tested `$exec.result.ok`, but `$exec` does not exist in that scope, so failed jobs were never marked error_retry or error_terminal.
- **Serial execution.** Images processed one at a time despite async-shared dispatch, making a 12 page story take around 13 minutes.

### Root cause of duplication

The lease was set at claim time with a 180 second window, but the async pool processed jobs serially over roughly 13 minutes. By the time later jobs started, their leases had long expired. The worker tick recovery block then saw expired leases on processing jobs and requeued them, and the next tick re-dispatched them, creating duplicate executor runs and duplicate paid image generations.

The fix is to extend the lease at execution start, in the same step that sets started_at, rather than relying on the claim time lease alone. This also makes the recovery reaper accurate, since a lease expiring after execution genuinely started is a real stuck job.

### Metadata API observability

Set up a third Postman collection, metadata, for the Xano Metadata API, alongside app and webhooks.

- Uses a separate privileged metadata access token, stored as its own environment variable, distinct from bearerToken. Flagged as highly privileged and not to be committed when versioning collections.
- Endpoint for function history is `GET /workspace/{workspace_id}/function_history`.
- Key discovery: the parameters (page, per_page, branch, function_id, include_output) are query string parameters on a GET, not a JSON body. Passing them in the body caused them to be silently ignored and the whole workspace history returned unfiltered. Confirmed against the Xano docs.
- Retention: function runs are kept 24 hours, background tasks 7 days, then wiped. This makes the executor_runs table the durable source of truth for outcomes, with the metadata history as a transient live timing view.

### End to end image test

Created story 606 via the API through the full creation flow, then fired page_text, which returned status In Queue with 13 jobs created (12 pages plus 1 cover) and images_remaining 12.

The run completed cleanly:

- **No duplicate executor runs.** Each job is a single record. The lease fix worked.
- Page images ran 19:23 to 19:45.
- Batch 1 (cover to page 4) completed first try in about 4 minutes.
- Batch 2 (pages 5 to 9) took 3 tries each.
- Batch 3 (pages 10 to 12) took 5 tries each.

The rising retry count per batch (1, then 3, then 5) points to OpenAI rate limiting later in the run, likely 429s from firing image requests faster than the tier allows. To be confirmed by inspecting error codes on the retried attempts via the metadata function history, since the executor_runs record keeps only the final success.
