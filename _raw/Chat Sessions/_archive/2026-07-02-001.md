## Decisions made

### user_alerts — action-only PATCH (no is_read toggle)
`PATCH /user_alerts/{id}` accepts no input; always sets `is_read: true`. Users cannot toggle unread. Rationale: standard inbox pattern (Gmail, Slack, Notion), preserves `read_at` audit trail, aligns with push notification badge semantics, minimises mutable surface. If "flag for later" is needed later, add `is_flagged` as separate field.

### user_alerts — Model A (account-level inbox)
`user_alerts.users_id` remains the sole ownership field. No `user_profiles_id` on alerts. All profiles in the household share one inbox. Rejected Model B (per-profile inboxes) as complexity multiplier: routing ambiguity, multi-device push registration challenges, no analogous UX pattern in kids' apps (Disney+, Netflix Kids, Duolingo ABC all use account-level). Profile context surfaced via message copy ("Emma's story is ready"). Retrofit to Model B remains cheap if needed post-launch — add nullable `user_profiles_id` and filter GET.

### Kids Mode UI as design north star
Child profile UI is content-shaped (bookshelf, e-reader, story creation, characters). Adult profile UI is dashboard-shaped (settings, billing, alerts, admin, orders). Reference model: YouTube Kids. This is a frontend concern with backend implications: some endpoints must remain parent-only at API level regardless of what the frontend renders (order creation, subscription mutations, delete profile, set PIN). Belt-and-braces: never rely on frontend hiding a button as security.

### V1 alert catalogue confirmed
Alerts that fire an inbox row:
- Story ready
- Story blocked (moderation)
- Story needs parental approval (moderation)
- Character creation complete (only if async — not V1)
- Order status: placed / shipped / delivered / issue (via webhook work)
- Subscription payment failed / trial ending (via Stripe webhook work)
- System announcements (via admin broadcast function, post-launch)

Explicitly not alerts:
- Login events, session refreshes, story views, page turns, auto-save, profile edits
- Story generation "started" (transient — in-session UI covers it)
- Onboarding complete (in-session celebration screen covers it)
- Welcome (transactional email, not inbox)
- Character creation complete when blocking/mid-chatbot (redundant with the surface the user is already on)

### Phonics — nested endpoint over flat listing
Rejected the security-model spreadsheet suggestion of exposing every phonics table as its own flat endpoint. App only needs scheme picker + nested stages tree. Grapheme/exception/mapping tables remain internal to the AI text-generation pipeline. Two endpoints total.

### Phonics — optional selection during onboarding, per-story override
`phonics_scheme_id` and `phonics_stage_id` added to `user_profiles` (nullable, set once, changeable) and to `instant_stories` (nullable, defaults to profile's stage, overrideable per story). Defaults to Tomale Phonics when unset. Rejected making selection required — reduces onboarding friction.

### Character creation — no completion alert (V1)
Character creation currently blocks UI with 30s spinner (acceptable). Future chatbot flow fires image generation mid-conversation; the chatbot itself becomes the notification surface ("I've drawn your character, take a look!"). Adding inbox alerts on top would be redundant. Rule: inbox alerts are for events the user might miss because they left the surface.

## Open items (deferred, needs decision or design)

### Wellbeing-sensitive content handling in moderation pipeline
The `flag_account` branch currently applies OSA-style silence uniformly. That's the right shape for Category A (adversarial CSAM, grooming, extremism) but wrong for Category B (user in distress — self-harm, suicidal ideation).

Category split needed pre-launch:
- **Category A** (CSAM, grooming, extremism, hate): silent block, full logging, evidence preservation, internal escalation, potential authorities notification via NCMEC/CEOP/IWF
- **Category B** (self-harm, suicide ideation, abuse disclosure, extreme distress): supportive user-facing response, age-appropriate resource surfacing (Childline 0800 1111, YoungMinds parent helpline 0808 802 5544, Papyrus HOPELINE247 0800 068 4141), parent inbox alert, ops human review, wellbeing monitoring flag (not suspension)
- **Category C** (violence, adult content prompts): current silent-block behaviour, pattern review

Requires:
- Moderation policy prompt evolution (surfacing category granularity in output)
- New alert type / urgency handling
- Curated UK safeguarding resource content
- Ops process for human review SLA (24-48h)
- Legal check on UK OSA mandatory reporting obligations
- Safeguarding consultation before launch (NSPCC / Childline offer this)

Log as pre-launch decision note and design pass. Not urgent to code, urgent to plan.

## Learnings / principles reinforced

- **Inbox alerts have a real cost — user attention.** Every unneeded alert erodes the value of the ones that matter. Fire alerts only for events the user might miss because they've left the surface. "The user is watching this happen" = no alert. "The user has closed the app" = alert.
- **Model A account-level inbox is right for family apps.** Kids don't triage their own alerts inbox. Content targeting comes through session context (which profile is active), not through separate inboxes per profile. Kids' apps in market (Disney+, Netflix, Duolingo) universally use this model.
- **Kids Mode UI is a product axis, not a settings menu.** The child profile is an entirely different UI surface — few controls, no admin, content-first. Designing every future feature with "how does this look for the child profile?" as a first-class question, not an afterthought.
- **Chatbot flows are their own notification surface.** When a user is actively in a chatbot conversation, the chatbot conveys system events conversationally ("I've drawn your character!"). Inbox alerts on top are redundant. Design chatbot-driven flows knowing the chatbot IS the notification channel during the session.
- **Silent moderation is the right shape only for adversarial actors.** OSA-style suppression protects evidence and prevents evasion for CSAM/grooming/extremism. Applied uniformly, it fails users in distress. Duty of care and safeguarding obligations require Category B (wellbeing) responses to be warm, supportive, and parent-notified — not silent.
- **Xano's PATCH routing conflicts when subpaths collide with `{id}` placeholders.** `PATCH /user_alerts/mark-all-read` matched `PATCH /user_alerts/{user_alerts_id}`. Resolved by POST verb on the bulk endpoint. Rule: named bulk actions use POST, single-record edits use PATCH.
- **Nested response shapes beat flat resource endpoints when the UI needs a tree.** Phonics picker needs scheme → phases → stages. One call returning the tree beats three calls + client-side joining. Purpose-built endpoints for the UI's actual data need, not raw table exposure.
