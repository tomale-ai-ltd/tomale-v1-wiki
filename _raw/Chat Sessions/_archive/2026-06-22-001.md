# Session note — 2026-06-22-001

> Implemented per-child story visibility on instant_stories end to end, ran the two backing migrations, and closed the legacy data gap. Next session moves to user_profiles CRU, then a Phase 1 reassessment.

## Focus

Scope a story to the profile that created it, enforce a child visibility and moderation gate on reads, and migrate legacy data so every account has a default profile and every story has a creator profile.

## What we did

- Added `user_profiles_id` to `instant_stories`. Populated on POST from `$auth.extras.active_profile.id`, server-side only, never a client input.
- Edited GET all `instant_stories`. Added the nested profile and moderation gate to the `where`. Parent profiles see all household stories, child profiles see only their own stories that have cleared moderation. Added `user_profiles_id` to the output.
- Edited GET one `instant_stories`. Applied the same gate inside the existing precondition so a disallowed story returns a 404 rather than the record. Covers another account, a sibling profile, a locked story, and a soft-deleted story with one indistinguishable not-found.
- Verified `is_child` is populated and non-null in extras on login, signup, and select_profile, not just present as a key.
- Confirmed the moderation pipeline sets `status_moderation` consistently across Pass, Fail, Parental Approval, and Pending.
- Rejected Xano's proposed fix that fell back to the default profile when extras was null. It was fail-open, silently elevating a missing-extras token to parent visibility. Replaced with a fail-closed resolution using `|get` and a null precondition, and test with a real Postman token instead.
- Ran `bulk_create_default_user_profiles`. Every account now has a default adult profile. 45 accounts, 49 profiles total including internal test child profiles.
- Ran `bulk_assign_user_profiles_to_stories`. Legacy stories with a null creator are backfilled to their account's default adult profile.
- Postman tested with both a child token and a parent token. Child sees only their own cleared stories and cannot pull a sibling's or a locked story via GET one. Parent sees everything including pending. POST writes `user_profiles_id` correctly from extras.

## Decisions

### D1 — Per-child story visibility model
- Decision: A story is visible only to its creator profile and to any parent profile on the same account. No cross-profile or cross-account sharing in V1. Single FK `user_profiles_id` on `instant_stories`, set server-side at creation. No join table in V1. Read enforcement lives in the endpoint, not the frontend.
- Status: accepted
- Note: [[per-child-story-visibility]]

### D2 — Fail-closed active profile resolution
- Decision: When `active_profile` cannot be resolved from extras, the endpoint fails closed with a re-login error. No fallback that elevates a missing-extras token to the default or parent profile. Test tooling gaps are solved with real tokens in Postman, not by weakening the endpoint.
- Status: accepted
- Note: reinforces the existing no-silent-privilege-escalation principle. Capture in principle log, standalone note optional.

### D3 — List and detail projection split
- Decision: GET all returns a lightweight card projection, GET single returns a curated detailed projection. The field difference is a UX and performance choice, not a security boundary. Anything that must never reach a client is excluded from both. The visibility gate controls who sees a story, the projections control how much.
- Status: accepted
- Note: principle, no standalone note required.

### D4 — Legacy story ownership on backfill
- Decision: Legacy stories with a null creator are assigned to their account's default adult profile, not left null. The adult default has `is_child == false` so it already sees all account stories, and child profiles never inherit legacy content. Backfill is for provenance and the future sharing feature, not a correctness fix.
- Status: accepted
- Note: covered within [[per-child-story-visibility]].

### D5 — Parental gate on profile switching
- Decision: Switching into a parent profile from a child profile must require an account-level PIN, verified server-side in select_profile. Proposed rule and select_profile sketch drafted. Not yet built.
- Status: proposed, open questions remain
- Note: [[parental-gate-on-profile-switch]]
