### Duplication root cause

The duplication had multiple compounding causes, resolved in order:

1. **Lease value written as epoch (1970).** `claim_image_jobs` computed `locked_until` using `$env.image_worker_lease_seconds` without casting to int. The env value arrived as text, `add_secs_to_timestamp` could not use it, and `locked_until` was written as epoch. A 1970 timestamp is always `<= now`, so the job was permanently re-claimable regardless of lease length. Fixed by casting the env var to int. Confirmed by isolated variable test: now + 1200 computed correctly.
    
2. **Claim-time lease was hardcoded to 180 seconds.** Even with the int fix, the claim lease was far shorter than the roughly 700 second claim-to-start gap caused by the slow async pool. Fixed to use the lease seconds env var so the claim lease survives until the executor picks the job up.
    
3. **Reaper had no grace period.** It requeued any processing job whose lease had just lapsed, including jobs still waiting in the async queue. Added `image_reaper_grace_seconds` (set to 300) subtracted from now, so only jobs genuinely well past their lease are reaped.
    
4. **Reaper incremented attempt.** A reap is a recovery action, not a failed try, but it was consuming an attempt, which could send healthy but slow-queued jobs to terminal prematurely. Removed the attempt increment from the reaper. Attempt now only increments on genuine claim in the tick. Confirmed the attempt versus priority mismatch (attempt 3, priority 60) was caused by this double counting.
    
5. **The real structural bug: error handling nested inside compiler success.** In the executors, the success and error branches all sat inside `if (compiler_status == 200)`. If the prompt compiler itself failed (a 429 under load), none of the branches ran, so the job was never marked complete or error. It stayed `processing` until the reaper requeued it, producing a second executor run in a later tick. This was the persistent cross-tick duplication after the lease fixes. Compounded by the error branches referencing `$exec.result` (a non-existent variable in executor scope) instead of `$result`, making them unreachable even when reached.
    

### Executor restructure

All three executors rewritten so terminal handling always runs, outside the compiler conditional. Every path (compiler failure, image failure, thrown exception, or unresolved) now ends by marking the job complete, error_retry or error_terminal. Nothing can be left processing.

Key elements of the new pattern:

- `$result` seeds as retryable so any unforeseen fall-through requeues rather than sticks.
- An `$image_called` flag guards references to `$openai_image`, so a compiler-stage failure (where the image response does not exist) cannot throw a missing-path fatal in the terminal handler.
- A single terminal conditional at the end: success, then retryable, then a catch-all else for terminal.
- `api_request` and `api_response` whitelisted (no auth header, no base64), built via an `$api_log` variable that stores compiler status when the image was never called.
- Added `simulate_compiler_error` and `simulate_image_error` boolean inputs (image only for the character executor, which has no compiler stage) to test the failure paths deliberately without calling OpenAI or editing live code. Default false, so production is untouched.

Per-executor specifics:

- **executor_page_image**: full compiler plus image, recount of pages without images for images_remaining. Fixed a leftover `error_message` showing on success (now cleared). Tested: happy path writes the page image and completes, both simulated errors land the job in error_retry in the database.
- **executor_cover_image**: full compiler plus image, writes cover_image on the story, no images_remaining. Tested: happy path updates the story record, both simulated errors work.
- **executor_character_image**: no compiler stage, single image call, writes to characters.cover_image (confirmed correct field name despite the odd name). Corrected the terminal branch, which previously set retry fields on a terminal failure. Tested: happy path updates the character record, simulated error works.

### Late issue in the worker tick

A worker tick issue caused the cover image and one page image to fail on a subsequent run. Because the `simulate` inputs (and by extension the input handling) were not set as defaults in the page and cover executors, the values had to be passed through from the async dispatch. When they were not, the executor_runs records were never created, so several executors failed at the run lookup. Resolved by correcting the input handling. Appears to be working now but a fully clean run has not yet been observed.
