## Decisions made

### Users group endpoint shape

- **`bool_*` preference endpoints collapsed** — `push_alerts`, `push_marketing`, `email_opt_in` folded into `PATCH /users/me` under a `preferences` object. `bool_email_verified` deleted (handled by `/auth/verify_email`). `bool_subscription` deleted (set internally by webhooks, never user-settable). `bool_onboarding` → its own `POST /users/me/complete_onboarding` event-style endpoint.
- **Image upload endpoint shape** — built `PATCH /users/me/image` only for V1. Explicit `PATCH /user_profiles/{id}/avatar` deferred until kid profile support arrives. When both exist, the convenience wrapper will call a shared internal function rather than duplicating logic.
- **Username is user-editable** — included in `PATCH /users/me` allow-list with uniqueness check, regex (`^[a-z0-9_]+$`), and lowercase normalisation. No email re-verification needed (username ≠ login email).
- **`last_modified_at` vs `opt_in_status_last_updated`** — these track different things and update on different triggers. `last_modified_at` set on any record edit; `opt_in_status_last_updated` only when consent fields change.

### Image storage approach

- **Public file storage (Xano native) retained for V1.** S3 + CloudFront migration parked until later in Phase 1 (or early Phase 2) — covered by AWS for Startups credits. Decision note authored and added to wiki. The endpoint contract (`PATCH /users/me/image`) doesn't change when storage backend swaps; only internals do.
- **Server-side image validation enforced** — mime, size, dimensions. No transform/EXIF strip available in current Xano plan; handled client-side via `expo-image-manipulator` instead. Server validates the result.
- **EXIF privacy concern noted but de-prioritised** — for V1, the only user-uploaded images are parent avatars (the kid's image comes from AI generation). Parent uploading their own photo only exposes their own home coordinates to themselves until storage becomes public-facing.

### Auth + verify_email

- **Reason-matching long-term fix queued** — Xano's `verify_email` endpoint should return structured `error_code` values (`TOKEN_EXPIRED`, `INVALID_USER`, etc.) instead of human-readable messages. Frontend-side substring matching is a V1 workaround. Added to "post-Phase-1 hardening" list.
- **Empty-string keys in Xano response** — observed `""` keys in `verify_email` response payload. Likely a malformed JSON object somewhere in the function stack. Worth tidying at source. Not breaking, but odd.

## Notes / scratchpad

- Idiomatic JS recap: `if (data.success)` is correct when API returns proper booleans. `=== true` only needed when distinguishing boolean true from other truthy values (e.g. `1`, `"false"` strings). Use `===` for strict equality always; avoid `==`.
- Convenience-wrapper pattern (`/users/me/image` → `/user_profiles/{id}/avatar`) only works DRY if both call a shared internal function. Otherwise rebuild diverges. Worth doing properly when kid profiles ship.
- Pattern B for image uploads confirmed: resource-specific endpoints, each owns its authorization, shared internal upload mechanics. Generic upload endpoint with a "context" parameter is an anti-pattern (collapses auth into a switch statement; breaks self-documentation; couples unrelated change cycles).
- Xano image transform unavailable on current plan — handle resize/EXIF strip client-side via `expo-image-manipulator`. Re-evaluate when on Lambda@Edge / CloudFront Functions post-S3 migration.
- `auth.extras.active_profile_id` proved its worth — avoided a profile-lookup DB roundtrip + made the endpoint work correctly for the multi-profile model. Worth using this pattern wherever an endpoint operates on "the currently-active profile."
