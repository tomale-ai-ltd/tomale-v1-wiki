### system / activities

**Context:** `activities` is the gamification challenge catalogue. Users earn points for completing activities (e.g. Sign Up = 1000 pts). Points are redeemable for discounts on hard copy books. A separate `user_activities` table tracks per-user completion — that will be handled in the `users` group.

**Endpoints reviewed:** GET (list), GET (single), POST, PATCH, DELETE — all currently public.

**Decisions:**

- **DELETE** POST, PATCH, DELETE endpoints — activities are admin-managed only, no app writes needed
- **DELETE** GET single — no use case for fetching a specific activity by ID; app works from the list
- **KEEP** GET list — auth required, with server-side filters:
    - `status = 'active'` (hardcoded — client never sees draft/inactive)
    - `open_date <= now()`
    - `expiry_date IS NULL OR expiry_date >= now()`

**Schema additions:**

Added `status` enum to the `activities` table:

|Value|Meaning|Visible in app?|
|---|---|---|
|`draft`|Created but not ready|No|
|`scheduled`|Ready, waiting for trigger|No|
|`active`|Live and earnable|Yes|
|`paused`|Temporarily hidden|No|
|`expired`|Past its run|No|
|`archived`|Soft-deleted by admin|No|

**Rationale for enum over boolean (`is_active`):** captures intent and state history, not just current on/off. Makes auto-activation logic cleaner. A future cron job can handle `scheduled → active → expired` transitions based on dates. For V1, statuses are flipped manually via Xano admin.

**Dates and status work together:**

- Dates = the planned window
- Status = the actual state
- This allows mid-month specials, surprise activations, and pausing without touching dates

**No soft delete** — reference data, admin-managed. No risk of accidental user deletion since the endpoint is removed.

### system / artwork_style

**Context:** Catalogue of available artwork styles users can select when generating a story. Records include access tier / plan level data (free vs premium). Decision made to return all styles to all authenticated users — the "peek under the kimono" approach to drive upgrades.

**Endpoints reviewed:** GET (list), GET (single), POST, PATCH, DELETE — all currently public.

**Decisions:**

- **DELETE** POST, PATCH, DELETE endpoints
- **KEEP** GET list — auth required, hardcoded `status = 'active'` filter. Returns all styles regardless of access tier.
- **KEEP** GET single — auth required, 404 if not found, 404 if `status != 'active'`

**On keeping GET single — steel-manned:** Initially suggested deleting the single-record GET. Kyle pushed back. Reasons to keep it:

1. Deep links (marketing emails, push notifications) may link to a specific style
2. Detail screens may fetch independently of the list (richer payload, separate cache TTL)
3. Upgrade flow CTA ("Unlock Watercolour") naturally links to a specific style ID
4. Cost of keeping is near-zero (two-step function stack)
5. Consistent with the rest of the API surface (instant_stories, characters all have detail endpoints) Decision: keep it.

**On access tier filtering:** Server should NOT filter by access tier. The full catalogue is returned. Frontend filters/segments in memory using the `access_tier` field on each row. This enables locked tiles with upgrade CTAs without extra network calls. The actual entitlement gate (preventing a free user from using a premium style) happens at the point of story creation, not at the point of display — consistent with `PRD-Subscription-Entitlement-System` Addition 3.

**Function stack — GET `/artwork_style`:**

1. Auth required
2. Query all WHERE `status = 'active'` (hardcoded)
3. Return

**Function stack — GET `/artwork_style/{id}`:**

1. Auth required
2. Get record by id
3. Precondition: record exists → else 404
4. Precondition: `status == 'active'` → else 404
5. Return

**Note for later (not Phase 1):** Entitlement enforcement for premium styles must be implemented at the story creation endpoint — verify the user's entitlement permits the selected `artwork_style_id` before committing the record.

### system / fact

**Context:** Frontend UI component. Displays a single informative or fun fact to the user. Serious literacy facts for parent/adult profiles; cheeky fun facts for child profiles. App presents one randomised item.

**Endpoints reviewed:** GET (list), GET (single), POST, PATCH, DELETE — all currently public.

**Decisions:**

- **DELETE** POST, PATCH, DELETE endpoints
- **REPLACE** GET list with a purpose-built `GET /fact/random` endpoint (randomisation server-side)
- **DELETE** GET single — no use case once random endpoint exists; app never fetches a specific fact by ID

**Rationale for server-side random:** smaller payload, cleaner API intent, no list logic on the client. Consistent with CTO plan section 2.5 (purpose-built endpoints over generic CRUD).

**Profile-aware fact filtering:** child profiles get child facts, adult profiles get adult facts. This led to a broader design discussion about how profile context is passed to the backend (see auth / select_profile section below).

**Function stack — GET `/fact/random`:**

1. Auth required
2. Conditional: `$auth.extras.is_child == true`
    - THEN: Query `fact` WHERE `type = 'child'`, random sort, LIMIT 1
    - ELSE: Query `fact` WHERE `type = 'adult'`, random sort, LIMIT 1
3. Precondition: record exists → else 404
4. Return

**Note:** If `is_child` is null (user hasn't selected a profile yet — token has no extras), ELSE branch fires and returns an adult fact. This is the correct safe default.

**Schema requirement:** `fact` table needs a `type` field (enum: `child`, `adult`) if not already present.

### auth / select_profile (new endpoint)

**Context:** Designing this endpoint led to a broader discussion about how profile context flows through the system. This is the most architecturally significant work of the session.

#### Background

The app supports multiple user profiles per account (parent + children). When a user selects an active profile, the backend needs to know which profile is active for all subsequent requests — without the client passing a `profile_id` on every call.

**Two options evaluated:**

|Option|Approach|Verdict|
|---|---|---|
|A|Issue a new auth token with `active_profile_id` + `is_child` embedded in extras on profile selection|✅ Best practice — chosen for V1|
|B|Client passes `profile_id` as input on every profile-aware request|❌ Fragile, more surface area, client trusted to pass correct value|

**Why Option A:**

- Backend owns session state, not the client
- No per-request profile ownership validation overhead
- Cleaner API contract — profile-aware endpoints read from auth context, not input
- Scales naturally to parental controls, per-profile entitlements, content filtering
- Industry standard: Netflix, Disney+, Spotify Kids, YouTube Kids all embed profile mode in session context

**Xano extras capability confirmed:** Xano supports custom fields in the auth token payload via `extras` JSON object. Set via `security.create_auth_token` with `extras = { "active_profile_id": 123, "is_child": true }`. Read in authenticated endpoints via `$auth.extras.active_profile_id` and `$auth.extras.is_child`.

**Important Xano caveat:** Quick test token generator does NOT include extras. Must test via a real login call (Postman) to get a token with extras populated.

**Endpoint:** `POST /auth/select_profile`

**Function stack:**

1. Auth required
2. Input: `profile_id` (integer, required)
3. Get record from `user_profiles` WHERE `id = input.profile_id` AND `users_id = auth.user.id`
4. Precondition: record exists → else 404 (ownership check — prevents profile hijacking)
5. Create auth token via `security.create_auth_token`:
    - `user_id = auth.user.id`
    - `extras = { "active_profile_id": input.profile_id, "is_child": profile.is_child }`
6. Return new token

**Frontend behaviour on receipt:** swap stored token in Zustand and AsyncStorage. New token replaces current one — this is a session continuation, not a new login.

**On user_sessions table:** A profile switch should UPDATE the existing session row (not insert a new one). Profile selection is a session continuation, not a new login. Inserting new rows per profile switch would cause session table bloat and complicate refresh token management.

#### Multi-profile architecture — V1 scope

Agreed to implement simple + medium tiers in V1:

**Simple (do now):**

- `POST /user_profiles` — create a profile (name, is_child)
- `POST /auth/select_profile` — token swap with extras ✅ built this session
- Auto-create default profile on signup (one step added to signup endpoint)
- `GET /user_profiles` — list profiles for the account (feeds selection screen)

**Medium (do now):**

- `PATCH /user_profiles/{id}` — edit profile name/avatar
- Profile switcher UI accessible mid-session

**Deferred:**

- Per-profile PIN/lock (parental controls)
- Per-profile entitlements/usage tracking
- Profile deletion with data handling

**Onboarding pattern:** user is forced to create at least one profile during onboarding before accessing the app. No way out. Auto-create a default profile on signup, or prompt immediately after.
