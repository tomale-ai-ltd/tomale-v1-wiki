## Decisions made

### 1. Profile model: unified table with is_child flag

Chose **Model B** over keeping `user_child_profiles` with implicit adult = null. Reasoning: cleaner mental model, supports future per-profile data (age, preferences, reading level), single FK target across the schema.

### 2. No profile deletion in V1

Per soft-delete discussion: deletion of profiles is complex (what happens to stories, characters, history, future recommendations data?). Decided:

- V1: no DELETE endpoint at all — parents can rename profiles
- Post-V1: implement soft-delete via `archived_at` column, with archived profiles excluded from selector but retaining their content

### 3. Token overwrite is the only auth state mechanism

Documented architectural decision (this session): old auth tokens are never invalidated — they expire naturally based on `exp` (24h). The frontend is the source of truth for "which token is active." Pattern:

- Single Zustand slot for `authToken` + `activeProfile`, persisted to AsyncStorage
- Every auth-response endpoint (login, signup, select_profile, refresh, reset_password) returns full state; frontend overwrites atomically via a single `setAuth()` handler
- App launch: rehydrate from AsyncStorage → call `/auth/me` → overwrite in-memory state with canonical Xano response
- Never decode JWT payload client-side — `/auth/me` is the only source of truth for profile context

Trade-off accepted: old tokens remain valid until expiry. Low risk in practice (tokens don't leave the device). Phase 2 could add server-side token revocation if needed.

### 4. Always default to is_default profile on login

Login looks up the user's `is_default = true` profile and bakes its values into the token extras. Means a parent who always uses a child profile gets bumped back to adult on every login. Acceptable for V1 (safer default, simpler logic). Post-V1 could add `users.last_active_profile_id` for "last used" behaviour.

### 5. users.profile_photo retired in favour of user_profiles.avatar

Column dropped. All displayable identity comes from profiles, not the account record. Cleaner separation: `users` for account-level concerns (auth, billing), `user_profiles` for displayable identity.

### 6. Email verification: full best-practice pattern adopted

- Unguessable random token (UUID stored as text)
- Single-use (nullified on consumption)
- 1-hour expiry (short, but accepted for V1)
- Branded landing page on Squarespace, not raw Xano JSON response
- Token never appears in URL bar after success (`history.replaceState`)

Rejected the "hit endpoint with raw user_id" hacky version on security grounds.

### 7. Stripe customer creation moved to post_process

Was blocking signup if Stripe API was slow/down. Now in post-process; user record is created first, Stripe customer created after, `stripe_customer_id` written via follow-up edit. Tolerates orphan customers (cost: zero) and Stripe outages.

Lazy creation pattern flagged for checkout endpoint: if `stripe_customer_id` is empty at checkout, create one then.

### 8. Resend variable shape requires explicit object wrapping

Discovered: Xano's `|set` filter on `variables` parameter only works correctly when the receiving function explicitly defines `object` type wrapping (not just `schema = {}`). Empty schema blocks get serialised as `[]`. Wiki convention: **always declare object schemas with sub-fields, or use untyped `object`/`json`, but never `object { schema }` with empty body**.

## Notes / scratchpad

- **Xano gotcha #1**: `object foo { schema }` with empty schema serialises as `[]` when populated via `|set` filter. Always declare sub-fields or use loose `object`/`json` type.
- **Xano gotcha #2**: `$auth.extras.foo.bar` throws hard error if any path segment is missing. Defensive `first_notempty` won't catch it — error happens at reference time, not evaluation time. Must guard by ensuring extras are always populated (i.e., fix login to issue them).
- **Xano gotcha #3**: Table label vs name distinction — `"user sessions"` in `db.add` is the table _label_, not name; both work.
- **Xano gotcha #4**: `first_notempty` only triggers on null in some contexts, not empty string. Behaviour depends on the consuming filter/operation.
- **Pattern for profile-aware endpoints**: read `$auth.extras.active_profile.is_child` directly. Falls cleanly when login is fixed to issue extras.
- **CORS**: confirm Xano workspace allows `tomale.ai` origin for the Squarespace verify-email page to call the API.
- **Email verification window**: 1 hour (3600 seconds via `add_secs_to_timestamp:3600`). Short. Acceptable for V1 given small user base.
