# Session Note — 2026-07-03-001

## Summary

Closed the store_orders group in Phase 1 with the full refactor: single-step POST with new order_number format, multi-step PATCH supporting the checkout flow, GET single with store_order_updates addon, GET all scoped list. Moved to transaction_webhook_events replacement scoping. Surfaced but deferred a V1 monetisation strategy decision.

## Endpoints completed

- **POST /store_orders** — refactored per decision note. Single db.add, no post-insert edit. New order_number format `TOM-{yyyymmdd}-{users_id}-{story_id}-{random4}`. Validates instant_story ownership and completion state before creating Draft.
- **PATCH /store_orders/{store_orders_id}** — multi-step checkout support. All fields optional, coalesced via `first_notempty` against the existing record. Fields: `message`, `products_id`, `shipping_options_id`, `shipping_name`, `shipping_phone`, `shipping_email`, `shipping_add1/2/town/postcode`, `country`. Draft-status gate. Server-side totals recomputation on every PATCH. Country → locale_data lookup → currency inference. Google Places address selection assumed on frontend.
- **GET /store_orders/{store_orders_id}** — scoped single, `store_order_updates` embedded via addon, projection excludes checkout_session_object/HPBC internals/PDF attachments.
- **GET /store_orders** — scoped list, newest first, minimal projection.

## Decisions made

### store_orders — single-step POST via new order_number format
Removed the create-then-edit pattern. Order number format `TOM-{yyyymmdd}-{users_id}-{story_id}-{random4}` embeds date + user + story + entropy, guaranteed unique without depending on the auto-generated `id`. Adds input validation preconditions before `db.add`, eliminating orphan Draft records on bad input.

### store_orders — products become SKU-level
Size and orientation moved onto `products` table as columns (one product row per SKU, e.g. "A4 Landscape Hardback"). Removed from `store_orders` entirely. Frontend picks `products_id`, size/orientation resolve via join. Prevents double-management between shipping/product tables and store_orders records. Standard print-on-demand pattern. Rejected variants table as over-engineered for V1.

### store_orders — Draft-only mutability (Option A, strict)
PATCH only allowed while `status == "Draft"`. Once payment initiates, order is immutable to the user. Post-payment changes and cancellations go through customer support (manual admin process). Rejected tiered mutability (cancel-with-refund via API) as over-scoped for V1 — Stripe refund flow, HPBC pull-back, partial fulfilment edge cases deserve their own decision note pre-launch. Support-driven flow acceptable at low volume.

### store_orders — server-side totals recomputation on every PATCH
`subtotal` (from product amount) and `shipping_amount` (from shipping_options amount) recomputed on every PATCH after coalescing effective `products_id` and `shipping_options_id`. Frontend displays what the backend returns — never calculates prices locally. Prevents drift, tampering, and stale pricing. Total is derived on read (subtotal + shipping_amount), not stored.

### store_orders — currency inferred from locale_data, not user-input
`country` accepted as PATCH input (from Google Places address select, uppercased on ingest). Country → locale_data lookup by `ISO3166-1-Alpha-2`. `locale_data_id` and `currency` (from `ISO4217-currency_alphabetic_code`) written to store_orders. Rejected currency-as-input to remove tampering surface. V1 restricts to GB with explicit precondition — users outside UK get 422 `SHIPPING_COUNTRY_UNSUPPORTED` rather than silent failure post-payment. All schema shape correct for future multi-currency; no migration needed when it ships.

### V1 monetisation strategy — deferred, not decided today
Surfaced a wider strategic question: should V1 include subscription mechanics (Stripe/IAP + entitlements + tier logic) or ship with book purchases only + restricted free tier + subscription as post-launch fast-follow? Decided this belongs in its own dedicated decision pass, not folded into Phase 1 hardening. Does not block transaction_webhook_events infrastructure work — table shape supports future providers regardless of when they wire up. See open items.

### transaction_webhook_events — same table for HPBC + Stripe (+ future Apple/Google)
Rejected separate tables. `transaction_webhook_events` becomes the generic provider-webhook ingress log — raw payload storage, dedup, replay. `provider` field treated as free text with index (not strict billing enum), naming expanded from "billing" to "provider webhook events". HPBC lands here despite not being a billing provider.

### transactions table remains money-only
HPBC events land in `transaction_webhook_events` for ingress logging but do NOT create `transactions` rows. HPBC drives updates to `store_orders` and `store_order_updates` instead. Money and fulfilment are separate domains — keeps `transactions` semantically clean.

### HPBC idempotency key — composite, not `_id` alone
HPBC's `_id` field is order-level (constant across all status callbacks for one order), not per-event. Using `_id` alone as dedup key would collapse status updates into a single event. Composite key required: `_id + status + timestamp` (option 1, cleanest, if HPBC callback body carries a per-event timestamp) or `_id + status` (option 2, workable if each status transition fires once per order). Decision to ship with option 2 initially with full callback body logging enabled for the first weeks post-launch to observe real behaviour and refine.

## Learnings / principles reinforced

- **Multi-step PATCH endpoints benefit from server-side derived state.** Totals, currency, locale — none should be inputs, all derived from other fields at write time. Frontend displays what backend returns. Client-side price math is drift and tampering surface.
- **SKU-level products beat variant modelling for V1.** Size + orientation as columns on `products` (one row per SKU) is dramatically simpler than a variants table and matches how print-on-demand is actually sold. Complexity earned only when catalogue grows past ~20 SKUs.
- **Strict Draft-only mutability keeps the API safe with acceptable UX cost.** Post-payment editing creates real reconciliation risk (Stripe checkout session invalidation, refund logic, partial fulfilment) — much larger than the customer service burden of "email us to change your order" at V1 volume.
- **`transaction_webhook_events` as generic provider ingress log outgrows its billing-focused name quickly.** Treating `provider` as free text with an index (rather than strict enum) future-proofs it for HPBC, Apple, Google, and anything else that arrives without schema surgery. Rename the mental model, not the table.
- **`transactions` table stays money-only.** Fulfilment events belong in `store_order_updates` and drive `store_orders` state. Domain separation makes both easier to reason about.
- **Idempotency key design starts with "what does the provider guarantee is unique per event."** HPBC `_id` looked unique but is actually per-order — the difference matters. Confirm dedup key against real payloads, not just documentation. Log everything for the first weeks post-launch to refine.
- **Monetisation strategy is not an API hardening decision.** Building t_w_e infrastructure is orthogonal to which providers get wired first. Strategy belongs in its own decision pass with founder-level scope — pricing, tiers, IAP vs web, timing.

Current SKU-level model works for small catalogue (~5-10 rows). If future catalogue exceeds ~20 SKUs across sizes, orientations, materials, cover types, revisit with a proper variants table (products → variants, one variant per SKU, product-level metadata deduplicated). Not V1 concern.

### Multi-currency architecture (deferred)
Schema shape correct for it — `locale_data_id` and `currency` already stored per order, driven by country. Multi-currency ship path when it arrives:
1. Add currency-specific price rows on products (`products_prices` join)
2. Add Stripe price IDs per currency (already partly present as `stripe_price_test`/`stripe_price_live` — expand)
3. Add HPBC (or replacement) region config
4. `locale_data` drives which combination fires at PATCH/checkout time
Zero schema surgery needed on `store_orders` when this lands.
