## What I actually did

- **Rebuilt `transaction_webhook_events`.** Deleted the drifted table and recreated it clean. There were no API or custom functions referencing it, so a rebuild was cheaper than several in-place migrations. Final shape carries `provider` (text), `external_id`, `event_type`, `dedup_key`, `status`, `retry_count`, `processing_errors`, `payload` (json, not attachment), `processed_at`, `created_at`, `last_modified_at`. Primary key is UUID.
- **No CRUD endpoints.** The table is internal only. All writes happen inside the webhook endpoints and the two shared custom functions using raw db blocks. Nothing external reads or writes it.
- **Indexes.** Unique index on `dedup_key` (the idempotency guard). Standard indexes on `status` (retry sweep filter), `provider`, and `created_at`. `provider` is low cardinality and marginal, retained cheaply, revisit with a composite once the retry task exists.
- **Built `webhook_event_ingest`.** Store-before-process plus dedup. Inserts the raw event, and on a unique-constraint violation the catch branch looks up the existing row and returns `is_duplicate: true` with the same event id. Insert-and-catch was chosen over query-then-insert to close the race window where two concurrent copies both see "not found".
- **Built `webhook_event_complete`.** Validates status first (only `success` or `failed`), reads the row, and sets `status`, `processed_at`, `processing_errors`, and increments `retry_count` on failure. Returns the input echo rather than internal state.
- **Wired `POST /stripe/webhook_payment_confirmation`.** Confirmed `util.get_raw_input` exposes the raw body, so signature validation is viable. The Stripe verification action is wrapped in Try/Catch so a bad signature fails closed with an opaque 401 rather than the raw package error. Dedup key composed inline as `stripe:{id}`. Flow is verify, ingest, duplicate short-circuit to 200, unknown-type store-and-ack to 200, process the order, run the PDF orchestrator inline, mark the event complete, return a bare 200.
- **Confirmed HPBC uses bearer token auth**, not a signature. That removes the raw-body dependency for HPBC and means a whole-string comparison against an env var, fail closed.
- **Established the extensibility seam.** A normalised internal event envelope with a `domain` field (`order` or `subscription`) and a router with both branches. Only the order branch is wired now. Apple and Google slot in later by adding a normalise function and the subscription handler, with no change to the table, the ingest function, the dedup logic, or the router.

## Decisions made

<!-- Filtered to items with architectural/product weight, cross-checked against constitution, data-model, api-spec, sdd-process-overview, PRD, build-plan, and CTO implementation plan. -->

- **`transaction_webhook_events` rebuilt rather than migrated in place.** Empty table, no references, so a clean rebuild was lower risk than six column migrations. Fills in implementation detail within the agreed CTO plan direction. No new decision note filed.
- **UUID primary key for `transaction_webhook_events`.** Switched from int during the rebuild. Defensible for an internal-only table whose ids never reach a client, and a UUID cannot be enumerated if one ever does leak. This contradicts `data-model.md`, which still says int, so it needs recording in the doc refresh. Confirm whether the switch was deliberate or a Xano default before it hardens.
- **No CRUD endpoints for the group.** Internal-only table. Writes go through the webhook endpoints and two shared custom functions. Consistent with CTO plan API surface reduction. No deviation.
- **Dedup via a unique index on a computed `dedup_key` plus insert-and-catch.** Chosen over a raw composite index and over query-then-insert. Race-safe because Postgres arbitrates the conflict. Confirms the direction scoped on 2026-07-03.
- **Two shared custom functions, dedup key composition stays inline per provider.** A provider switch inside the shared function would defeat the point, so each endpoint composes its own key.
- **Unknown event types are stored and acked with 200, not rejected.** Stripe retries any non-2xx, so rejecting an unhandled type would cause retry storms. The event is stored and marked success.
- **Two opposite failure responses.** An ingest failure (event never stored) returns 500 so the provider retries, since re-send is the only recovery. A processing failure (event already stored) returns 200, marks the event failed, and retries internally from the stored payload.
- **Backend observability is a launch requirement, not a Phase 2 nice-to-have. DECISION NOTE REQUIRED.** Confirmed with Xano support that there is no native Sentry integration. Backend error reporting must be built manually with Try/Catch plus an External API Request to Sentry's event endpoint with the DSN in headers. This is a build task, unestimated in the current plan. The webhook ingest, retry, and processing paths are backend only and invisible to a frontend-only Sentry install, so launching without backend observability means money and fulfilment paths fail silently. The alternative, Xano native Error Logs plus its own alerting, costs nothing to build and should be stated and rejected explicitly in the note rather than defaulting to Sentry. This supersedes the Phase 2 "frontend minimum" wording in section 8.1 and Phase 2 task 15.

## Notes / scratchpad

**Learnings captured this session:**

- Xano Try/Catch does catch a unique-constraint violation rather than aborting the whole stack. This is what makes insert-and-catch dedup viable, and it was proven, not assumed.
- `util.get_raw_input` exposes the raw request body, so Stripe HMAC signature validation over the exact bytes is achievable.
- The Stripe verification package throws a fatal error on a bad signature, which fails closed, but the raw error is a 500 with a leaky message. Wrapping it in Try/Catch converts it to a clean opaque 401 and stops Stripe retrying a malformed delivery forever.
- Test harness fidelity matters. A hardcoded id in the Postman pre-request script silently collapsed three distinct test events into one dedup key. Two tests appeared to pass but never ran. The signed raw body is the source of truth, not the Postman body tab, and editing the body tab alone changes nothing the endpoint sees.
- HPBC bearer token gives authentication but no payload integrity, so a captured body can be replayed. The dedup unique index is what absorbs that risk, which is a second reason it earns its place.
- Apple and Google notifications do not carry the user id. It must be stamped at purchase time and cannot be recovered later.

**Future PRD / build direction items captured, not yet committed:**

- Normalised internal event envelope (`domain`, `type`, `owner_user_id`, `provider`, `external_id`, `occurred_at`) as the subscription-ready seam. Both router branches built, only the order branch wired.
- Optional nullable `owner_user_id` on `transaction_webhook_events`, populated at normalise, useful for support queries. Cheap now, annoying to backfill later.
- Interim HPBC dedup weakness, two events for the same order at the same status get swallowed as duplicates. Post-launch callback body logging confirms whether a timestamp is needed in the key.
