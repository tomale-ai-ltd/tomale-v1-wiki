## What I actually did

### `users` endpoint group — restructuring (complete)

Deleted 5 endpoints that were unsafe or superseded: `GET /users` (exposed all user records publicly), `GET /users/{users_id}` (replaced by `/auth/me`), `POST /users` (replaced by `/auth/signup`), `DELETE /users/{users_id}` (account deletion deferred — GDPR concern parked), and `POST /users/{users_id}/bool_email_verified` (now handled by `/auth/verify_email`).

Restructured 3 endpoints around the authenticated user:

- `PATCH /users/me` — auth-derived (`$auth.id` for read and write), strict allow-list (`first_name`, `last_name`, `about_me`, `username`, `preferences.push_alerts`, `preferences.push_marketing`, `preferences.email_opt_in`). Sensitive fields (`subscription_active`, `plan_level`, `email_verified`, etc.) excluded from the allow-list and stripped from the response. Validates username uniqueness, regex and case. `last_modified_at` always set to `now`; `opt_in_status_last_updated` updates only when consent fields change.
- `POST /users/me/complete_onboarding` — idempotent, no body required (auth context provides the user). Skips re-stamping when `onboarding_complete` is already true. Bumps `last_modified_at` and a new `onboarding_completed_at` column added to the `users` table.
- `PATCH /users/me/image` — writes to `user_profiles.avatar` (not `users.profile_photo`), uses `$auth.extras.active_profile_id` to target the profile, with a defence-in-depth ownership check (`profile.users_id == $auth.id`). Server-side validation: mime (jpeg/png/webp), 5 MB size cap, dimensions 200×200 min / 2048×2048 max. Old avatar deleted from Xano storage after a successful DB write. `access = "public"` for V1 with a TODO to switch to private + signed URLs on the S3 migration.

### Carryover item #8 — Squarespace `/verify-email` page (complete)

- Replaced the `YOUR_AUTH_GROUP_ID` placeholder with the real auth group ID (`1pgd39RE`); endpoint URL is now `https://api.tomale.ai/api:1pgd39RE/auth/verify_email`.
- Fixed a reason-matching bug — the page compared `data.reason === 'expired'` but Xano returns `"expired token"`; switched to `data.reason?.includes('expired')`.

## Decisions made

Most of today's work restructures the `users` group and therefore deviates from `api-spec` and `data-model` as currently written. These are tracked for reconciliation under carryover item #5, and pending decision notes under carryover item #6 (now 8 total — see Next session).

- **Image storage — formal deviation, decision note exists.** Public file storage (Xano native) is retained for V1; the S3 + CloudFront migration is deferred to later in Phase 1 / early Phase 2 (covered by AWS for Startups credits). Captured in [[Project/Decisions/migrate-image-storage-to-aws-s3-signed-urls|migrate-image-storage-to-aws-s3-signed-urls]]. The endpoint contract (`PATCH /users/me/image`) is stable across the backend swap — only internals change.
- **`bool_*` preference endpoints collapsed** into `PATCH /users/me` under a `preferences` object. `bool_email_verified` deleted (handled by `/auth/verify_email`); `bool_subscription` deleted (set internally by webhooks, never user-settable); `bool_onboarding` promoted to its own event-style `POST /users/me/complete_onboarding`. Deviates from `api-spec`.
- **Image upload endpoint shape** — only `PATCH /users/me/image` built for V1. An explicit `PATCH /user_profiles/{id}/avatar` is deferred until kid-profile support lands; when both exist they will share an internal upload function rather than duplicate logic.
- **`username` is user-editable** — included in the `PATCH /users/me` allow-list with uniqueness check, regex `^[a-z0-9_]+$`, and lowercase normalisation. No email re-verification needed (username ≠ login email).
- **`onboarding_completed_at` column added to the `users` table** — a `data-model` addition requiring reconciliation (carryover #5).
- **Server-side image validation enforced** (mime, size, dimensions). Resize / EXIF strip handled client-side via `expo-image-manipulator` since the current Xano plan has no image transform; the server validates the result.

## Notes / scratchpad

- Idiomatic JS: `if (data.success)` is correct when the API returns a real boolean. `=== true` is only needed to distinguish boolean `true` from other truthy values (`1`, `"false"`). Always use `===`; avoid `==`.
- The convenience-wrapper pattern (`/users/me/image` → `/user_profiles/{id}/avatar`) only stays DRY if both call a shared internal function — otherwise the rebuild diverges. Do it properly when kid profiles ship.
- Pattern B confirmed for image uploads: resource-specific endpoints, each owning its own authorization, sharing internal upload mechanics. A generic upload endpoint with a `context` parameter is an anti-pattern — it collapses auth into a switch statement, breaks self-documentation, and couples unrelated change cycles.
- Xano image transform is unavailable on the current plan — handle resize / EXIF strip client-side. Re-evaluate at Lambda@Edge / CloudFront Functions after the S3 migration.
- `$auth.extras.active_profile_id` avoided a profile-lookup DB roundtrip and made `PATCH /users/me/image` correct for the multi-profile model. Reuse this pattern wherever an endpoint operates on the currently-active profile.
- Long-term fix queued (post-Phase-1 hardening): `verify_email` should return structured `error_code` values (`TOKEN_EXPIRED`, `INVALID_USER`, etc.) instead of human-readable strings; the frontend substring match is a V1 workaround.
- EXIF privacy: de-prioritised for V1 — the only user-uploaded images are parent avatars (kid images are AI-generated), and a parent uploading their own photo only exposes their own coordinates to themselves until storage becomes public-facing.
