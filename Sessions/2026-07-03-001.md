## What I actually did

- **POST /store_orders** — refactored to single-step create (removed create-then-edit pattern). New `order_number` format `TOM-{yyyymmdd}-{users_id}-{story_id}-{random4}`. Validates `instant_story` ownership and completion state before creating the Draft.
- **PATCH /store_orders/{store_orders_id}** — multi-step checkout support. All fields optional, coalesced via `first_notempty` against the existing record (`message`, `products_id`, `shipping_options_id`, shipping address fields, `country`). Draft-status gate. Server-side totals recomputation on every PATCH. Country → `locale_data` lookup → currency inference.
- **GET /store_orders/{store_orders_id}** — scoped single, `store_order_updates` embedded via addon, projection excludes checkout-session internals/HPBC internals/PDF attachments.
- **GET /store_orders** — scoped list, newest first, minimal projection.
- **Schema:** moved `size`/`orientation` from `store_orders` onto `products` (SKU-level, one row per SKU); removed from `store_orders` entirely.
- **API security audit:** `store_orders` group closed (POST, PATCH, GET single, GET all); Draft-only mutability model confirmed. Began scoping `transaction_webhook_events` as the shared ingress log for HPBC + Stripe (+ future Apple/Google) — infrastructure scoped this session, wiring is next session's work.

## Decisions made

<!-- Filtered to items with architectural/product weight, cross-checked against constitution, data-model, api-spec, sdd-process-overview, PRD, build-plan, and CTO implementation plan. -->

- **`store_orders` products become SKU-level** — size/orientation moved onto `products` as columns (one row per SKU) instead of a variants table. Standard print-on-demand pattern for a small catalogue; revisit with a proper variants table only if catalogue exceeds ~20 SKUs. Fills in schema detail not previously specified in `data-model`; no contradiction, so no new decision note filed.
- **`store_orders` PATCH is Draft-only (Option A, strict)** — once payment initiates, the order is immutable to the user; post-payment changes go through customer support. Rejected tiered mutability as over-scoped for V1. Consistent with the CTO plan's data-integrity direction; no new decision note filed.
- **Totals, currency, and locale are always server-derived, never accepted as PATCH input** — matches CTO implementation plan §2.7/§3.7 (no endpoint returns/accepts data without server-side validation). No deviation.
- **`transaction_webhook_events` becomes a single generic provider-webhook ingress log** (HPBC + Stripe + future Apple/Google), with `provider` as free-text-with-index rather than a strict enum. Fills in webhook-security detail already required by CTO plan §2.6; no deviation.
- **`transactions` stays money-only** — HPBC events log to `transaction_webhook_events` and drive `store_orders`/`store_order_updates` state, not `transactions` rows. Domain-separation judgment call, doesn't contradict any documented plan.

None of today's decisions contradict the constitution, data-model, api-spec, PRD, build-plan, or CTO implementation plan — they fill in implementation detail within already-agreed direction. No new `Project/Decisions/` note was required.

## Notes / scratchpad

**Learnings captured this session:**
- Multi-step PATCH endpoints benefit from server-side derived state — totals, currency, locale should never be inputs; frontend displays what the backend returns.
- SKU-level products beat variant modelling for V1's small catalogue; complexity earned only past ~20 SKUs.
- Strict Draft-only mutability keeps the API safe at acceptable UX cost — post-payment editing risk (Stripe session invalidation, refunds, partial fulfilment) outweighs the support burden at V1 volume.
- `transaction_webhook_events` as a generic provider ingress log outgrows its billing-focused name quickly — treat `provider` as free text with an index, not a strict enum, to avoid schema surgery when Apple/Google arrive.
- Idempotency key design should start from "what does the provider guarantee is unique per event" — HPBC's `_id` looked unique but is actually per-order, not per-event. Confirm against real payloads, not documentation.
- Monetisation strategy is not an API-hardening decision — it's orthogonal to which webhook providers get wired first, and belongs in its own founder-level decision pass.

**Future PRD / build direction items captured, not yet committed:**
- Multi-currency architecture — schema already shaped for it (`locale_data_id`, `currency` per order); no `store_orders` schema surgery needed when it ships.
- Restricted free-tier design (rate limiting, usage tracking, reset cadence) — deferred pending the monetisation strategy decision.
- Cancel + refund flow — pre-launch decision note needed before scheduling.
