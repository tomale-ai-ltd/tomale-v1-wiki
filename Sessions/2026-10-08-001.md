## What I actually did

**Resolved the four order-fulfilment questions:**
- **Payment hop** — Stripe CLI (`stripe listen`) for a one-off signed-webhook proof that also exercises the Phase 1 task-6 signature validation; a dev-only simulate flag for the repeatable harness. Uses the existing Stripe test-mode product/price IDs on the `products` row, so no real money.
- **store_order minting** — confirmed the two-step pattern is correct and the harness uses the real path: `POST /app/store_orders` (Payment Pending) → `PATCH` draft fields → `GET /app/stripe/create_checkout_session`.
- **HPBC sandbox vs. simulate** — neither. There is no sandbox; the `_staging` SKUs route to the live Brand Centre but are rejected before production. Decided to run the real DB-trigger cascade end to end against a staging SKU, because that is the only way to exercise HPBC's print-file **preflight** on our PDFs. Simulating the callback would skip the one thing worth proving.
- **PDF-ready signal** — poll on `cover_pdf` AND `inner_pdf` attachments being non-null (the `status` enum has no "PDFs rendered" value); then assert `hpbc_order_id` set as the cascade-success signal.

**Clarified the live mechanism from Kyle's flow diagram:** fulfilment is not an endpoint call — it is a DB trigger (`order_fulfilment_check`) that fires on the PDF-write edit, gated on (payment Confirmed AND both PDFs AND `hpbc_order_id` empty AND `hpbc_lock` false) → `reconcile_order_fulfilment` → `hpbc_create_order`, synchronously. This means a dev payment run auto-submits to HPBC with no natural seam to stop at — which is why the staging-SKU approach (not a simulate branch) is the right call.

**Confirmed staging arrangement with Pureprint (print supplier, contact: Alex):** staging SKUs `TOM-001_staging` and `TOM-002_staging` are accepted into Brand Centre and run print-file checks, but never go to production. Go-live sequence agreed: send staging orders on both SKUs → Alex confirms Pureprint-side → one order per **live** SKU (real print, real cost) → production opens. Alex asked to be told once staging test orders are sent. Confirmed no HPBC charge on a staging/rejected order.

**Drafted the order-fulfilment flow-test build spec** (`order-fulfilment-flow-test-build-spec.md`, delivered to chat, pending filing into the vault). Three async-gated phases (A drive-to-payment, B PDFs+cascade, C HPBC terminal state), full assertion scripts, run matrix across the two flags and both staging SKUs. Run 1 doubles as discovery of the real terminal status of a valid staging order (expected Cancelled — passes `1_order_confirmed`, then staging reject → `5_order_cancelled` — but HPBC decides; lock the assertion after run 1).

**Reviewed `hpbc_create_order` XanoScript and fixed four issues** (Kyle applied):
- Null-user check was positioned after the `test_mode` branch so it never ran — moved `$user == null` to first condition (throw, since this authorises a real-world/print action).
- Failure branch set `hpbc_lock = false` with `hpbc_order_id` empty → re-armed the DB trigger into an infinite HPBC retry loop. Fixed to set `status: Error` and leave `hpbc_lock = true` so the gate stays closed.
- `preflight: true` (and `unitWeight`/`description`/`sourceComponentId`) had been dropped from the inline `components` vs. the agreed `print_specification` — restored; preflight is the whole point of the staging run.
- Test and live branches were duplicated except for the SKU field — collapsed to set `$sku` once then one shared lambda + `api.request`, removing drift risk.

**Added test-mode gating to `papermill_generate_pdf_cover` and `papermill_generate_pdf_inner`** (Kyle applied): `pdf_force_success` (canned vault PDFs) now also requires the order's user to be `test_mode = true`, so it can never substitute a stand-in PDF on a live customer order. Implemented via get-user + a null-safe `$use_test_pdf` flag defaulting to false (real docgen). Here a null user falls through to real docgen rather than throwing — fail-closed means "do the real thing" when the flag only selects a cheaper internal path, as opposed to the HPBC case where a bad read authorises a real action and must throw.

**Settled the identity-lookup pattern for trigger-fired internal functions:** use `store_order.users_id`, not `$auth.id`. There is no auth context in a trigger-fired run (`$auth` is empty and reading a missing path is a hard fatal), and `users_id` is server-established ownership, not forgeable client input — provided order create/patch strips client-supplied `users_id` (to verify).

## Blockers / questions

- **Postman monitor/folder structure.** Postbot proposed nesting Phase A/B/C as sub-folders under an Orders folder, but monitors run on whole folders — which would run the three async phases in one pass, where B and C (PDF attachments, HPBC callbacks) fail because the waits haven't elapsed. Flagged that A/B/C should be top-level sibling folders so each is independently runnable/monitorable. Needs a decision on whether phases run manually per-phase or as separate scheduled monitors before the restructure is finalised.
- **Live SKU strings** (`TOM-001` / `TOM-002` or as issued) to be confirmed with Alex before any live-SKU run — do not derive by stripping `_staging`.
- **`test_mode` flag reachability** inside `hpbc_create_order` at the point the DB-trigger cascade fires (different entry point than checkout) — to verify.
- **Order create/patch must strip client-supplied `users_id`** — verify, since the trigger-fired identity lookup trusts `store_order.users_id`.
- **Terminal status of a valid staging order** is unknown until run 1 (discovery); assertion `C1b` stays commented until confirmed.
- **Suspected logic bug in the Papermill functions** (carried for separate review): the terminal `elseif` branch reads `$result.ok && $result.retryable == false`, which is unreachable (a true `ok` already matched the success branch); likely should be `$result.ok == false && ...`, else a non-retryable failure via the `try` path never sets `pdf_jobs.status = error_terminal` and the job sticks.
- Fatal (`error_terminal`) simulation on the image executors still only reasoned through, not run — carried from [[2026-08-04-001]], still optional.

## Decisions made

- **HPBC/Pureprint environment switch keyed off the Stripe `test_mode` flag** — significant; decision note drafted (`DN-hpbc-environment-switch`, delivered to chat, **pending filing into `Project/Decisions/`**). Staging vs. live SKU is selected from the same per-user `test_mode` flag that already drives Stripe, so the dangerous mismatched state (test payment + live print, or vice versa) is unreachable. Adds `hpbc_sku_staging`/`hpbc_sku_live` (currently named `hpbc_sku_test`/`hpbc_sku_live` in code — reconcile) on `products`; SKU injected into `print_specification.sku` at call time; fail-closed to staging. Interim measure that overlaps CTO Phase 2 (dev/prod separation, tasks 10–11) and should retire in favour of environment-driven selection once real environments exist.
- **Keep `pdf_force_success` and `test_mode` as two orthogonal flags** — do not fold docgen-skip into `test_mode`. Collapsing them would make the key go-live test (test_mode + real docgen → real PDFs through HPBC preflight) impossible. `force_success` grabs a known-good vault PDF and still runs real HPBC preflight, so it isolates Papermill from the HPBC wiring. Test tooling / safety-gating detail within existing scope — no separate decision note.
- **Fail-closed philosophy for the mode flags:** throw when a flag authorises a real-world action (money/print/live SKU — the `hpbc_create_order` null-user case); default to the full real path when a flag only selects a cheaper internal shortcut (the docgen `force_success` case). No separate note.
- **Identity in trigger-fired internal functions uses `store_order.users_id`, not `$auth.id`** — consistent with the security model (point 2.2 is about untrusted request input, which this is not). No separate note.
