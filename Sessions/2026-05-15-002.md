## Decisions made

These deviate from / extend the plans in `Project/Plan/` and warrant standalone notes in `Project/Decisions/`:

- **Two-group Xano API structure (`app` + `webhooks`)** — replaces the seven-group structure implied by earlier `api-spec` content. Driven by the OpenAPI codegen's single-`servers:`-URL assumption and a cleaner production-API convention. Decision note pending.
- **Magic link URL strategy: `https://` web intermediary, not custom `tomale://` scheme** — emails carry a standard https link to Squarespace, which prompts the user to open the app. Trade-off: extra "Continue" tap in the browser; deferred Universal Links / App Links work to remove it. Decision note pending.
- **Strict env validation, no hardcoded fallbacks anywhere** — `config/env.ts` throws at startup in all environments (dev included) if required vars are missing. Rationale: surface misconfiguration loudly rather than letting silent fallbacks mask drift. Decision note pending.
- **EAS env config lives in `eas.json` (version-controlled), not the EAS dashboard** — dashboard reserved for real secrets only. Non-secret `EXPO_PUBLIC_*` values are PR-reviewable and reproducible.
- **Per-profile env blocks set up now even though all profiles point at the same Xano** — forward-compatible for the dev/prod Xano split at zero cost.
- **Magic link bearer issued by dedicated endpoint, never embedded in the URL** — email link carries a single-use magic-link token only; `POST /auth/complete_magic_link` exchanges it for a bearer + refresh. Aligns with the API security model's bearer-handling rules.

No deviations from `constitution`, `data-model`, `api-spec`, `sdd-process-overview`, `1-prd-tomale-react-native-app-v1`, `2-build-plan`, or `5-cto-implementation-plan` beyond the points listed above (which all extend rather than override those documents).
