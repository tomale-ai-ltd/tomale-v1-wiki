## What I actually did

- **Rebuilt `transaction_webhook_events`.** Deleted the drifted table and recreated it clean — no API or custom functions referenced it, so a rebuild was cheaper than several in-place migrations. Final shape: `provider` (text), `external_id`, `event_type`, `dedup_key`, `status`, `retry_count`, `processing_errors`, `payload` (json, not attachment), `processed_at`, `created_at`, `last_modified_at`. UUID primary key.
- **No CRUD endpoints.** Internal only — all writes happen inside the webhook endpoints and the two shared custom functions via raw db blocks.
- **Indexes.** Unique index on `dedup_key` (idempotency guard); standard indexes on `status` (retry sweep filter), `provider`, and `created_at`.
- **Built `webhook_event_ingest`.** Store-before-process plus dedup — inserts the raw event, and on a unique-constraint violation the catch branch looks up the existing row and returns `is_duplicate: true` with the same event id. Insert-and-catch chosen over query-then-insert to close the race window where two concurrent copies both see "not found."
- **Built `webhook_event_complete`.** Validates status first (`success`/`failed` only), reads the row, sets `status`, `processed_at`, `processing_errors`, increments `retry_count` on failure.
- **Wired `POST /stripe/webhook_payment_confirmation`.** Confirmed `util.get_raw_input` exposes the raw body, making HMAC signature validation viable. Stripe verification wrapped in Try/Catch so a bad signature fails closed with an opaque 401 instead of a leaky raw error. Dedup key composed inline as `stripe:{id}`. Flow: verify → ingest → duplicate short-circuit to 200 → unknown-type store-and-ack to 200 → process order → run PDF orchestrator inline → mark complete → bare 200.
- **Confirmed HPBC uses bearer token auth, not a signature** — no raw-body dependency; fail-closed whole-string comparison against an env var.
- **Established the extensibility seam.** Normalised internal event envelope with a `domain` field (`order`/`subscription`) and a router with both branches. Only the order branch is wired; Apple/Google slot in later via a normalise function and the subscription handler, no change to table, ingest function, dedup logic, or router.

## Decisions made

<!-- Filtered to items with architectural/product weight, cross-checked against constitution, data-model, api-spec, sdd-process-overview, PRD, build-plan, and CTO implementation plan. -->

- **`transaction_webhook_events` rebuilt rather than migrated in place.** Empty table, no references — clean rebuild was lower risk than six column migrations. Fills in implementation detail within the agreed CTO plan direction; no new decision note filed.
- **UUID primary key for `transaction_webhook_events`** — switched from int during the rebuild. Defensible for an internal-only table whose ids never reach a client. **This contradicts `data-model.md`, which still specifies int** — needs recording in the doc refresh, and confirmation on whether the switch was deliberate or a Xano default before it hardens.
- **No CRUD endpoints for the group.** Internal-only table; writes go through the webhook endpoints and two shared custom functions. Consistent with CTO plan API surface reduction — no deviation.
- **Dedup via a unique index on a computed `dedup_key` plus insert-and-catch**, chosen over a raw composite index and over query-then-insert. Race-safe because Postgres arbitrates the conflict. Confirms the direction scoped on 2026-07-03.
- **Two shared custom functions; dedup key composition stays inline per provider** — a provider switch inside the shared function would defeat the point.
- **Unknown event types are stored and acked with 200, not rejected** — Stripe retries any non-2xx, so rejecting an unhandled type would cause retry storms.
- **Two opposite failure responses** — an ingest failure (event never stored) returns 500 so the provider retries; a processing failure (event already stored) returns 200, marks the event failed, and retries internally from the stored payload.
- **Backend observability is a launch requirement, not a Phase 2 nice-to-have — DECISION NOTE REQUIRED.** Confirmed with Xano support there is no native Sentry integration; backend error reporting must be built manually (Try/Catch + External API Request to Sentry's event endpoint). Unestimated in the current plan. Webhook ingest, retry, and processing paths are backend-only and invisible to a frontend-only Sentry install, so launching without this means money and fulfilment paths fail silently. The alternative — Xano native Error Logs plus its own alerting — costs nothing to build and should be stated and rejected explicitly rather than defaulted away. **This supersedes the Phase 2 "frontend minimum" wording in §8.1 and Phase 2 task 15 — a manual decision note in `Project/Decisions/` is required before this hardens.**

## Notes / scratchpad

**Learnings captured this session:**
- Xano Try/Catch does catch a unique-constraint violation rather than aborting the whole stack — proven, not assumed. This is what makes insert-and-catch dedup viable.
- `util.get_raw_input` exposes the raw request body, so Stripe HMAC signature validation over the exact bytes is achievable.
- The Stripe verification package throws a fatal error on a bad signature (fails closed), but the raw error is a leaky 500. Wrapping it in Try/Catch converts it to a clean opaque 401 and stops Stripe retrying a malformed delivery forever.
- Test harness fidelity matters — a hardcoded id in the Postman pre-request script silently collapsed three distinct test events into one dedup key. Two tests appeared to pass but never ran. The signed raw body is the source of truth, not the Postman body tab.
- HPBC bearer token gives authentication but no payload integrity, so a captured body can be replayed. The dedup unique index absorbs that risk too.
- Apple and Google notifications do not carry the user id — it must be stamped at purchase time and cannot be recovered later.

**Future PRD / build direction items captured, not yet committed:**
- Normalised internal event envelope (`domain`, `type`, `owner_user_id`, `provider`, `external_id`, `occurred_at`) as the subscription-ready seam. Both router branches built, only the order branch wired.
- Optional nullable `owner_user_id` on `transaction_webhook_events`, populated at normalise — cheap now, annoying to backfill later.
- Interim HPBC dedup weakness — two events for the same order at the same status get swallowed as duplicates. Post-launch callback body logging should confirm whether a timestamp is needed in the key.
