## What I actually did

### system / activities — locked down

- Removed POST, PATCH, DELETE, and GET-single endpoints (admin-managed catalogue, no app writes, list-only access from app).
- Kept GET list as auth-required, with hardcoded server-side filters: `status = 'active'`, `open_date <= now()`, `expiry_date IS NULL OR expiry_date >= now()`.
- Added a `status` enum (`draft`, `scheduled`, `active`, `paused`, `expired`, `archived`) instead of a boolean `is_active` — captures intent and history, sets up cleaner future cron-driven activation transitions.

### system / artwork_style — locked down

- Removed POST, PATCH, DELETE.
- Kept GET list and GET single, both auth-required, both hardcoded to `status = 'active'`. GET single returns 404 if not found or non-active.
- Confirmed the policy: server returns the full catalogue regardless of access tier; the app filters/segments client-side and renders locked tiles + upgrade CTAs. Entitlement enforcement is deferred to story creation, consistent with `PRD-Subscription-Entitlement-System` Addition 3.
- Steel-manned keeping GET single — deep links, separate detail-screen payloads, upgrade CTAs that link to a specific style id, parity with `instant_stories` / `characters`. Cost of keeping is near-zero.

### system / fact — replaced with purpose-built endpoint

- Removed POST, PATCH, DELETE, GET list, and GET single.
- Replaced with `GET /fact/random`, which branches on `$auth.extras.is_child` to return a random child or adult fact (`type` enum on the table). ELSE branch is the safe default when extras are absent.
- Schema requirement noted: `fact.type` enum (`child`, `adult`).

### auth / select_profile — designed and (mostly) built

The most architecturally significant work of the day. New endpoint: `POST /auth/select_profile`.

- Function stack: auth-required → input `profile_id` → fetch `user_profiles` WHERE `id = input.profile_id` AND `users_id = auth.user.id` → 404 if not found (this is the ownership check) → mint new auth token via `security.create_auth_token` with `extras = { active_profile_id, is_child }` → return token.
- Frontend behaviour: swap the stored token in Zustand + AsyncStorage. This is a session continuation, not a new login.
- `user_sessions` rule: profile switch UPDATEs the existing session row, does not insert a new one (avoids table bloat and refresh-token complications).

Settled the architectural question that surfaced from the `fact` work: how does profile context flow through the system?

- **Chosen:** Option A — embed `active_profile_id` and `is_child` into the auth token's `extras` on profile selection. Backend owns session state.
- **Rejected:** Option B — client passes `profile_id` on every profile-aware request. Too much surface area, trusts the client.
- Aligns with how Netflix / Disney+ / YouTube Kids handle profile mode in session context.

### Multi-profile V1 scope agreed

- **Simple (this phase):** `POST /user_profiles`, `POST /auth/select_profile` (built today), auto-create a default profile on signup, `GET /user_profiles` for the selection screen.
- **Medium (this phase):** `PATCH /user_profiles/{id}`, mid-session profile switcher UI.
- **Deferred:** per-profile PINs, per-profile entitlements/usage tracking, profile deletion + data handling.
- Onboarding pattern: a profile must exist before the app is usable — auto-create on signup or force-prompt immediately after.
