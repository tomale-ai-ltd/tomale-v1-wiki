**`user_profiles` API surface — complete**

**`POST /auth/select_profile` — built and working**
- Inputs: `profile_id` (uuid, required). Verifies ownership, then issues a new token with `extras.active_profile.{id, name, is_child}` populated. Response: `{authToken, active_profile}`.

**Email verification — end-to-end and tested**

## Decisions made

The following are decisions made today that warrant either confirmation against canonical docs or a standalone note in `Project/Decisions/` (several appear to deviate from or extend the data model / api-spec assumptions and should be reconciled).

1. **Profile model: unified `user_profiles` table with `is_child` flag (Model B).** Chosen over keeping `user_child_profiles` with implicit "adult = null". Cleaner mental model, supports future per-profile data (age, preferences, reading level), single FK target across the schema. *→ Decision note recommended in `Project/Decisions/` — this is a data-model change.*
2. **No profile DELETE endpoint in V1.** Deletion is complex (stories, characters, history, recommendations data). V1: parents can rename profiles. Post-V1: soft-delete via `archived_at` with archived profiles hidden from the selector but content retained.
3. **Token overwrite is the only auth-state mechanism.** Old auth tokens are never invalidated server-side; they expire naturally on `exp` (24h). Frontend is the source of truth for "which token is active." Single Zustand slot for `authToken` + `activeProfile`, persisted to AsyncStorage. Every auth-response endpoint (login, signup, select_profile, refresh, reset_password) returns full state; frontend overwrites atomically via a single `setAuth()` handler. App launch: rehydrate → call `/auth/me` → overwrite in-memory state with canonical Xano response. Never decode JWT payload client-side — `/auth/me` is the only source of truth for profile context. Trade-off accepted: old tokens remain valid until expiry; low risk in practice since tokens don't leave the device. Phase 2 may add server-side revocation if needed. *→ Decision note recommended — this is an architecture-level pattern not previously documented.*
4. **Login always defaults to the `is_default = true` profile.** A parent who normally uses a child profile gets bumped back to adult on every login. Accepted for V1 (safer default, simpler logic). Post-V1: could add `users.last_active_profile_id` for "last used" behaviour.
5. **`users.profile_photo` retired in favour of `user_profiles.avatar`.** All displayable identity comes from profiles, not the account record. Cleaner separation: `users` for account-level concerns (auth, billing); `user_profiles` for displayable identity. *→ Decision note recommended — data-model change.*
6. **Email verification: full best-practice pattern.** Unguessable random token (UUID stored as text); single-use (nullified on consumption); 1-hour expiry; branded landing page on Squarespace, not a raw Xano JSON response; token stripped from URL after success via `history.replaceState`. Rejected the "hit endpoint with raw `user_id`" hacky variant on security grounds. *→ Decision note recommended if not already covered in api-security-model — verification token lifecycle is a security-model addition.*
7. **Stripe customer creation moved to `util.post_process`.** Was blocking signup if Stripe was slow/down. User record is created first; Stripe customer created after; `stripe_customer_id` written via follow-up edit. Tolerates orphan customers (cost: zero) and Stripe outages. Lazy-creation pattern flagged for the checkout endpoint: if `stripe_customer_id` is empty at checkout, create one then.
8. **Resend variable shape requires explicit object schema wrapping.** Xano's `|set` filter on the `variables` parameter only works correctly when the receiving function explicitly declares `object` type with sub-fields (not `object { schema }` with an empty body — that serialises as `[]`). Wiki convention going forward: **always declare object schemas with sub-fields, or use untyped `object`/`json`; never use `object { schema }` with an empty body**.

## Notes / scratchpad

**Xano gotchas captured this session (worth lifting into a Xano-conventions note later):**
- `object foo { schema }` with an empty schema serialises as `[]` when populated via the `|set` filter. Always declare sub-fields, or use loose `object` / `json`.
- `$auth.extras.foo.bar` throws a hard error if any segment of the path is missing — error happens at *reference* time, not evaluation time. `first_notempty` does **not** catch it. Guard by ensuring extras are always populated (i.e., fix login/signup to issue them).
- Table label vs name distinction: `"user sessions"` in `db.add` is the table *label*, not the name; both work.
- `first_notempty` only triggers on null in some contexts, not on empty string. Behaviour depends on the consuming filter/operation.

**Profile-aware endpoint pattern:** read `$auth.extras.active_profile.is_child` directly. Now that signup, login, and `select_profile` all populate extras, this falls cleanly.

**Email verification window:** 1 hour (`add_secs_to_timestamp:3600`). Short, but acceptable for V1 given the small user base. Revisit if support load increases. No `/resend-verification` page yet — deferred to Phase 2.
