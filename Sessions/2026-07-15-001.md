## Blockers / questions

- **Full payment-to-fulfilment end-to-end test deferred.** The Stripe transaction write is unit-verified but not yet tested through the whole chain (payment to transaction to fulfilment trigger to HPBC create to callbacks), because too many parts were in flux. Now that both HPBC callback endpoints work, this end-to-end run is unblocked and should be done next. Folds together with confirming the HPBC trigger URL fix (the destinations were pointed at an old Xano API location, which is why the earlier callback never landed).
- **HPBC error dedup key collision (deliberate, known).** Because both error triggers send `status: "Error"`, the error endpoint key is always `hpbc_error:{hpbc_order_id}:Error`. A second, different error on the same order (submission error then production error) collides and is swallowed as a duplicate. Accepted: the customer-facing status is Error either way, support handles it, and the operational detail is in the HPBC dashboard. The lost item is only the second audit row, not customer state. The payload carries no field to distinguish the two error types, so preserving both would require a timestamp in the key, which reintroduces the retries-look-unique problem. Not worth it.
- **Worker submit-on-success check still open.** Confirm the PDF worker only submits to HPBC on a successful render, not on any completed job. Carried from 2026-07-14.
- **Delivery status not tracked.** Callbacks stop at Shipped. Tracking-link scraping for delivery confirmation is possible but parked as a future item, not worth a carrier integration or aggregator cost for V1. Shipped-with-tracking-link is the terminal customer state.
- **`hp_webhook_token` and Stripe secret exposure.** The HPBC bearer token and a Stripe test session id were pasted into working chat during this session. Rotate the HPBC token and ensure the new value is set in both the Xano env var and the SiteFlow trigger configs so they stay in sync.

## Decisions made

<!-- Filtered to items with architectural/product weight, cross-checked against constitution, data-model, api-spec, sdd-process-overview, PRD, build-plan, and CTO implementation plan. -->

- **Record structured transactions and drop `checkout_session_object`.** Full decision note filed at [[record-transactions-drop-checkout-session-object]]. Payment facts belong in the money domain (`transactions`), not on the fulfilment record. Finishes the 2026-07-03 decision that Stripe normalises to a `transactions` row. Sequencing decided: schema restructure and money write in scope now, refund and cancel flow deferred.
- **Refund model split into two paths (recorded, build later).** Self-service cancel before production is a state-gated automated full refund, gated on pre-HPBC-submission, and `refundable_amount` serves this path only. Misprint and quality refunds are support-driven and discretionary, likely resolved via an account credit, which is a separate future ledger and does not touch `refundable_amount`. Captured in the decision note.
- **Money stored as integer minor units, not decimal.** `amount_minor` int plus `currency`, matching Stripe's native representation, replacing the float `price`. Avoids float rounding errors in refund arithmetic. Paired with `currency` so non-100-minor-unit currencies stay correct.
- **HPBC callbacks are the customer-facing status surface, six statuses only.** Order Confirmed, In Production, Shipped, Cancelled on the success endpoint, Error (both error triggers) on the error endpoint. Full HPBC operational granularity stays in the HPBC dashboards, deliberately not surfaced to the customer. Both error types collapse to a single Error status, with specific detail preserved in the `store_order_updates` message.
- **HPBC dedup key confirmed as `hpbc:{hpbc_order_id}:{status}`.** The field is `hpbc_order_id`, not `_id` as the docs implied, confirmed against a real captured payload. No `TimeStamp` in the key, since retries may not preserve it.
- **HPBC webhook endpoints are public with in-stack bearer verification.** Not Xano auth-table authentication, because HPBC is an external service with no user account or JWT. This is the shared-secret webhook case that CTO plan sections 2.1 and 2.6 explicitly allow. The in-stack check is the sole guard, so it must be fail-closed and a whole-string compare.
- **New `Project/Architecture/` folder for system-flow docs.** System flows and their function contracts live here. Function internals stay in XanoScript comments where reality checks them. Established during the documentation-strategy discussion.

## Notes / scratchpad

**Learnings captured this session:**

- Money should be stored as integer minor units, never decimal. Float types cannot represent many money values exactly, and the error accumulates across refund arithmetic. Store what Stripe sends (an integer) paired with its currency, and divide only for display, without hardcoding divide-by-100 since not all currencies have 100 minor units.
- Webhook endpoints authenticate the caller, not a user, so they are public with an in-stack shared-secret or signature check, not Xano auth-table authentication. There is no user account for an external service to authenticate against.
- A bare 200 response looks identical across the happy path, the duplicate branch, and the failed-order branch. The response code alone proves nothing. Always check the resulting data (TWE row status, order status, update log) to know which path actually ran.
- Confirm payload field names against a real callback, not documentation. HPBC's field is `hpbc_order_id`, not the `_id` the docs implied. The wrapper `_id` is HPBC's own log-record id and never reaches the endpoint.
- Delegating to an existing function (`hpbc_update_order`) inside the ingest pattern works cleanly, and its throw-on-missing-order behaviour is what lets the Try/Catch mark the event failed correctly. Verified by firing a bogus order id and seeing a `failed` TWE row with no order edit.
- Every `function.run` needs an `as` binding in XanoScript even when the result is unused, or the script errors.
- Documentation levels: system flows and function contracts are high-value and low-drift, worth authoring and maintaining. Function internals are low-value and high-drift, best left in code comments where they self-check. Spend documentation effort on the why (decisions) and the seams (system flows), which code cannot hold.

**Future direction items captured, not yet committed:**

- Account credits ledger for the support-driven refund path (separate table, future).
- Delivery-status tracking via carrier or aggregator (parked).
- Project-management RAG and knowledge-graph layer over the Obsidian vault. Keep documentation as plain markdown with rich wikilinks and consistent frontmatter, name functions by their exact name in prose so the entity graph stays dense, and treat the generated `Wiki/` layer as rebuildable output. Do not build the RAG layer yet, and do not distort present documentation for a future model. The external productisation of this (handing a software client a clean knowledge base at build handover) is a genuine idea but a separate business, captured and parked so it does not derail the current build.
