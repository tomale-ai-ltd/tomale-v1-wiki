## What I actually did

- **GET /user_alerts/{user_alerts_id}** — single alert, scoped to authenticated user, 404 on cross-account or missing.
- **PATCH /user_alerts/{user_alerts_id}** — mark alert as read. Action endpoint, no input required; always sets `is_read: true` and `read_at: now`.
- **PATCH /user_alerts/mark-all-read** — bulk mark-all-read for the authenticated user. Returns `updated_count`. Named as a subpath (not a bare PATCH) to avoid a Xano routing collision with the single-alert PATCH.
- **notifications/create_user_alert** — internal function (`users_id`, `type`, `title`, `message`, `action_url`, `action_label`). Internal only, never exposed publicly.
- **GET /phonics_schemes** and **GET /phonics_schemes/{id}/stages** — read-only scheme picker + nested phases/stages tree in a single call.
- **Injected `create_user_alert` into three call sites:** content moderation blocked branch, content moderation parental-oversight branch, and `story_completion_check` (guarded by the existing `status == "Preparing"` precondition to prevent duplicate alerts from concurrent image jobs). The `flag_account` moderation branch was deliberately left silent (see Blockers).
- **Schema changes:** added `user_alerts.action_url`, `user_alerts.action_label` (both nullable text); added `user_profiles.phonics_scheme_id`, `user_profiles.phonics_stage_id`, `instant_stories.phonics_scheme_id`, `instant_stories.phonics_stage_id` (all nullable uuid, defaulting to Tomale Phonics when unset).
- **API security audit:** closed `user_alerts` (all four endpoints + internal creator) and `phonics_phase_stage`/`phonics_scheme_phase` (replaced with the nested endpoint above). Confirmed `stripe/check_order_paid` and `stripe/create_checkout_session` correctly classified in the `app` group.

## Blockers / questions

- **Wellbeing-sensitive content handling is not yet designed.** The `flag_account` moderation branch applies silent-block uniformly, which is correct for Category A (CSAM, grooming, extremism) but wrong for Category B (self-harm, suicidal ideation, abuse disclosure) — those need a supportive response, resource surfacing, parent alert, and human review, not silence. Needs a pre-launch decision note, safeguarding consultation (NSPCC/Childline), and a legal check on UK OSA mandatory-reporting obligations. Flagged urgent-to-plan, not urgent-to-code.
- **`/instant_stories/:id/phonics` endpoint needs a mini-PRD** — the phonics data model doesn't yet link stories/pages to stages; design debt precedes the build.
- **Character-name moderation** deferred until character work resumes (`content_moderation_name` vs. a separate more-permissive row).

## Notes / scratchpad

**Learnings captured this session:**
- Inbox alerts cost user attention — fire only for events the user could miss because they left the surface; no alert if "the user is watching this happen."
- Account-level (Model A) inbox is right for family apps — kids don't triage their own alerts; profile context comes through message copy, not per-profile inboxes.
- Kids Mode UI is a distinct product surface (bookshelf/e-reader/content-first), not a filtered adult UI — reference: YouTube Kids. Some endpoints (orders, subscriptions, delete profile, set PIN) must stay parent-only at the API level regardless of frontend rendering.
- Xano PATCH subpaths can collide with `{id}` placeholder routes — named bulk actions should use POST, single-record edits PATCH.
- Nested response shapes (scheme → phases → stages) beat flat resource endpoints when the UI needs a tree.

**Future PRD ideas captured, not yet committed:**
- "Conversational notifications" section for the chatbot PRD — the chatbot becomes the primary notification channel during its own sessions.
- Kids Mode UI PRD — dedicated design pass (nav, screen inventory, interaction patterns).
