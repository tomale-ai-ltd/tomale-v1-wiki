## What I actually did

- **Phase 1 item resolution.** Reviewed all nine Phase 1 items against actual state. Item 5 (endpoint removal) confirmed complete against the API security model sheet. Item 8 (ownership model) resolved — `users_id` confirmed as the ownership field standard in practice rather than `owner_user_id`. Item 9 (soft delete) confirmed complete, done incrementally during the API security model work. Item 7 (internal endpoint protection) closed with no work required: Xano custom functions aren't HTTP reachable, so the AI pipeline and docgen functions need no internal key gate, and the four `instant_stories/{id}/*` endpoints are already user-authenticated with ownership scoping.
- **Closed loose flags from 2026-07-15.** HPBC bearer token rotated and updated in Xano. HPBC trigger URLs confirmed pointing at the correct Xano webhook endpoints.
- **`stripe_create_customer` hardening.** Removed the client-supplied `environment` input (Stripe test/live is determined by which secret key is used, not a client flag). Added an idempotency key (`customer_create_{users_id}`) so a lost response on a successful call doesn't create a duplicate customer on retry — required adding `users_id` as a function input. Reshaped the response to `{status, id}` so callers can branch on outcome. Caught and fixed a malformed header (`Idempotency Key` → `Idempotency-Key`) during initial testing; verified idempotency by firing the same call twice and getting the same customer id back.
- **Built `reconcile_stripe_customers`.** Background task scheduled at 900s that queries `users` for missing `stripe_customer_id` under a retry cap of 5, calls `stripe_create_customer`, and writes the id on success or bumps `stripe_customer_retry_count` / `stripe_customer_last_attempt_at` on failure. Two new fields added to `users` for this. First run reconciled 41 existing users (test-mode Stripe customers); second run correctly found zero rows.
- **Authored `order-fulfilment-flow-test-scripts.md`.** Covers Stripe → Papermill → HPBC. Set A: six isolated stage tests for fast regression. Set B: one continuous end-to-end run against a real Stripe test payment, for pre-launch sign-off. Written as Given/When/Then, authored as Postman assertions rather than a manual checklist so the same work covers the manual run now and the deferred Newman/CI suite later.
- **Postman testing suite setup.** Imported both Xano API groups (`app`, `webhooks`) via OpenAPI 3.0 spec import so collections stay spec-linked for future re-syncs. Created the `TOMALE-RN-V1-DEV` environment with shared auth/test values. Adopted `bearerToken` as the token variable name to match the import convention.
- **Auth pre-request script.** Built a collection-level pre-request script that logs in and refreshes the token only when stale. Initial JWT-decode approach failed — discovered Xano issues JWE (encrypted) tokens, not JWS, so claims can't be read client-side. Reworked to a time-based approach: store login timestamp + known 3600s TTL, check that instead of the token. Verified: first send issues and stores a token, second send reuses it with no refresh logged.
- **Found and fixed an `instant_stories` regression.** `POST /instant_stories` threw `ERROR_FATAL` reading `extras.active_profile_id` — a flat path that predates the `active_profile` nested-object change. Fixed to read the nested `extras.active_profile.id` path and removed `user_profiles_id` as a client input (profile context should come from token extras only). Retested, confirmed 200. First real regression the Postman suite has surfaced — validates the approach, since Xano's built-in test runner doesn't pass `auth.extras` and would never have caught this.

## Notes / scratchpad

**Learnings captured this session:**

- Xano issues JWE, not JWS, tokens — encrypted payload, no client-side claim decoding possible. Any expiry/claim logic (Postman scripts, and eventually the React Native frontend) must use a stored value, never the token itself. The frontend will need to source profile context from an endpoint and hold it in state rather than reading it off the token.
- Custom functions in Xano aren't HTTP reachable, so internal-key gating only applies to actually exposed endpoints, not the function layer beneath them.
- Stripe test vs. live mode is determined entirely by which secret key is used — no environment flag or mapping needed, which is why the client-supplied `environment` input was removed from `stripe_create_customer`.
- Idempotency keys guard against a specific failure mode: the provider call succeeding but the response being lost, followed by a retry. Not just simple duplicate-call protection.
- Frontend resumption sequencing agreed as: close Phase 1 → account/secret hardening → dev/prod split → blocking CI security stage → resume frontend work, starting with Sentry integration.
