# RS-2026-11-04-02: Read EXPO_PUBLIC env vars statically so release bundles inline them

- Change: `config/env.ts` read `process.env[name]` dynamically. Expo only inlines `EXPO_PUBLIC_*` values written as static `process.env.EXPO_PUBLIC_X`, so Release bundles had no API base URL; the strict startup check threw, and Expo's error recovery aborted (SIGABRT on `expo.controller.errorRecoveryQueue`). Debug dev builds were unaffected. Pre-existing since the strict env check ([[enforce-strict-env-validation-at-startup]]), found by the first preview build after SDK 58. Fix: static reads; keep the fail-fast check. Check the repo for any other dynamic `process.env[` reads.
- Speckit impact: none
- Process: edit, own commit in PR #20 (approved by Kyle in session 04/11 as part of fixing the PR C test failure)
- Verify: `APP_VARIANT=preview npx expo run:ios --configuration Release` launches to Sign in on the simulator; a fresh EAS preview build launches on the iPhone; `rg "process\.env\[" --glob '!node_modules'` returns nothing in app code
- Status note: applied 04/11 in PR #20 (rebase-merged into `main`): `d58568b` (static `process.env.EXPO_PUBLIC_API_BASE_URL` read). Verified: CI `test` green; EAS development and preview iOS builds install side by side as "Tomale Dev" and "Tomale"; `tomale://` and `tomalerntest://` open the matching app; preview build launches and signs in; magic link opens Tomale Dev (backend still sends `tomalerntest` links until the Xano split).
