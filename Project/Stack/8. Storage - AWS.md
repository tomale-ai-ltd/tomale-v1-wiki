# AWS S3

## Actual vs. intended usage

### Actual (evidenced in the 'tomale-rn-test' repo)

- The app and contracts clearly model **media/file objects** and consume URL-based media:
  - `instant_story_pages.image`, `characters.cover_image`, story-level `cover_image` / `cover_photo`, and attachment-style PDF fields are present in the data model and OpenAPI-generated types.
  - Frontend currently renders story art from URL fields (e.g. `cover_photo.url`) in UI.
- Xano endpoints include media-oriented operations (e.g. story attachment/image endpoints and inline PDF retrieval), indicating backend-managed file handling.
- **What is not directly provable from this repo:** the storage provider being specifically AWS S3, bucket names, or signed URL policy in production.

### Intended (as described by architecture direction)

- Use AWS S3 as backing object storage for generated images and PDFs.
- Keep upload/retrieval orchestration in Xano, with frontend consuming backend-returned file URLs.
- Move from broadly accessible asset URLs toward tighter access control (e.g. signed URLs) where needed.

## Key endpoints / schema highlights

- Asset-bearing entities in schema/docs:
  - `instant_story_pages.image`
  - `instant_stories` media fields (including cover image/photo + story PDF fields)
  - `characters.cover_image`
  - order/print-related PDF fields (`cover_pdf`, `inner_pdf`, plus PDF job tables)
- Media-related API surface in OpenAPI excerpt:
  - Story media mutation endpoints (image/attachment on `instant_stories`)
  - Character image endpoint (`/characters/{characters_id}/image`)
  - PDF retrieval endpoint (`/view-pdf-inline`)
- Access pattern (current observable shape):
  - Backend exposes file metadata/URL-like fields -> frontend renders via image components.

## Version / environment

- **Confirmed:** media storage is backend-managed through Xano contracts and consumed by Expo app via URL/file payloads.
- **Not confirmed in repo artifacts:** explicit S3 bucket configuration, dev/prod bucket split, signed URL enforcement strategy, or IAM-level setup.
- Suggested wording for docs:
  - “Object storage provider is intended to be AWS S3 via Xano integration; operational bucket/security details are managed in backend environment configuration.”

## Known gotchas

- Storage provider assumptions can drift from reality if not documented from backend infra source of truth.
- Public media URLs are convenient but risky for private/family content.
- Inconsistent key naming/path conventions become costly for debugging and retention policies.
- Large media payloads impact app performance without resizing/compression/caching discipline.
- Overwrite/version behavior should be explicit (especially for regenerated covers/pages/PDFs).
