# Sentry  
  
## How we use it  

We use Sentry for error tracking and basic observability, primarily on the React Native frontend to capture runtime errors, crashes, and failed API calls. It provides visibility into real user issues that are not detectable through manual testing alone.  
  
## Key endpoints / schema highlights  

### Captured events:  

- App crashes  
- Runtime exceptions  
- Failed API requests

### Desired Future Scope:

Context enrichment (attached to events):  
- `user_id`  
- `child_profile_id`  
- `feature` (e.g. story_creation, reading)  
- `entity_id` (e.g. story_id)  

Key flows monitored:  
- Story creation + generation  
- E-reader usage  
- Store + checkout flow

Alerts:  
- Triggered on repeated errors or spikes  
- Sent via email (V1)  
  
## Version / environment

- SDK: `@sentry/react-native` (Expo-compatible integration)
- Environment split in app runtime:
- `development` in dev builds
- `production` in non-dev builds
- DSN is environment-config driven (`EXPO_PUBLIC_SENTRY_DSN`)
- Backend/Xano observability integration is not represented as a first-class implementation in this frontend repo
  
## Known gotchas  

- Only useful if errors are actually triaged — otherwise it becomes noise.  
- Over-logging creates alert fatigue quickly.  
- Missing context (user_id, feature, etc.) makes errors hard to debug.  
- Backend visibility is limited unless explicitly instrumented in Xano.
