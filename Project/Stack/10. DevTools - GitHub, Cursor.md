# Cursor (IDE), GitHub

## Actual vs. intended usage

### Actual (evidenced in this repo)

- GitHub hosts the codebase and is wired to GitHub Actions workflows:
  - `CI` workflow runs on PRs to `main` and executes `npm ci`, `lint`, `typecheck` (if script exists), and tests.
  - `Release (main)` workflow runs on pushes to `main`, installs deps, computes release metadata, and logs release info.
- The repo uses PR-oriented flow toward `main` (CI trigger is explicitly `pull_request` -> `main`).
- Local developer tooling is set up for quality gates:
  - `husky` + `lint-staged` configured in `package.json`.
  - Lint/test scripts exist (`lint`, `test`, `test:ci`).
- Cursor is explicitly part of project standards documentation (`Developer Tools: Cursor IDE + SpecKit`) but IDE-level usage details are not directly enforceable in code.

### Intended (documented direction)

- Trunk-based workflow with short-lived feature branches and protected `main`.
- CI gates should be strict and sequential (`lint -> typecheck -> unit tests`) and required for merges.
- Broader security automation (audit/secrets/static analysis) is planned in DevOps docs, but not fully represented in committed workflows yet.
- Cursor is intended as the primary AI-assisted IDE for implementation, refactoring, and spec-driven development.

## Key workflow / integration highlights

- GitHub repository + Actions workflows are the source of truth for CI/release automation in this repo.
- CI currently targets code health/test reliability; release workflow currently focuses on release metadata tracking.
- OpenAPI/schema workflow is codified in scripts (`update:openapi`, `codegen:openapi`) and expected to run through normal PR flow.
- Pre-commit quality tooling is present, but enforcement strength depends on team discipline + branch protection configuration in GitHub settings.

## Version / environment

- **Cursor:** used locally by developers (exact installed version is machine-specific, not tracked in repo).
- **GitHub:** hosted source control + CI platform.
- **CI runtime/tooling (confirmed):**
  - Node version from `.nvmrc`
  - `npm ci`
  - `npm run lint --if-present`
  - `npm run typecheck --if-present`
  - `npm test -- --runInBand`
- **Not currently present in workflows:** explicit `gitleaks`, `semgrep`, or `npm audit` jobs.

## Known gotchas

- `typecheck` is referenced in CI with `--if-present`; if the script is missing, that gate silently skips.
- “Planned security checks” can create false confidence unless explicitly added as required CI jobs.
- Branch discipline/protection cannot be verified from code alone; it depends on GitHub repo settings.
- AI-assisted coding (Cursor) increases speed, but consistency still depends on human review and standards enforcement.
