# Manual Testing

## Actual vs. intended usage

### Actual (evidenced in repo)

- Manual validation is actively used in specs/checklists (Given/When/Then acceptance flows and validation checklists across auth, Zustand, observability, and HTTP slices).
- CI includes automated test execution (`npm test -- --runInBand`) on PRs to `main`.
- Automated coverage is currently very light in practice:
  - A minimal smoke test exists (`.tests/smoke.test.ts`).
  - No enforced coverage thresholds are configured in `jest.config.js` or workflows.
- Current implemented app flows in code are mostly around auth/bootstrap and basic story listing; full moderation/order pipeline testing is not yet demonstrably represented in app-side tests.

### Intended (documented direction)

- Manual testing is the primary V1 safety net for end-to-end user journeys in real app builds.
- Validation should happen on device builds (Dev Client / EAS builds) against real backend behavior.
- Specs expect scenario-based validation for launch/login/logout/session persistence, resilience, and release checks.
- As slices mature (AI pipeline, payments, fulfillment), manual testing alone is expected to be insufficient and should be complemented by stronger automated coverage.

## Key workflow / validation highlights

- Current manual style in project docs:
  - Acceptance scenarios written in Given/When/Then form.
  - Checklist-driven validation per feature slice.
  - Real integration behavior emphasized over heavily mocked tests.
- CI test gate exists, but currently validates only a thin automated layer.
- Manual checks are especially important today for:
  - Auth/session continuity
  - Hydration/fallback behavior
  - Release/observability sanity checks

## Version / environment

- Test runtime/tooling:
  - Jest (`jest-expo` preset, jsdom environment)
  - PR CI runs install + lint + typecheck + tests
- Manual environments (documented and used by process):
  - Local/dev app runs
  - Device-oriented validation via Dev Client/EAS workflows
- No coverage threshold enforcement configured at this time.

## Known gotchas

- Manual quality depends on checklist discipline and consistency across contributors.
- Critical regressions can slip through because automated tests are currently minimal.
- Complex async/back-end-heavy flows (retries, queue workers, webhooks, race conditions) are hard to validate reliably by hand.
- “CI green” may not imply meaningful behavioral confidence until test depth increases.
