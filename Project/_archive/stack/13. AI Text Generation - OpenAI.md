# OpenAI GPT-4o

## How we use it

We use GPT-4o (primarily via structured JSON outputs) to generate children’s story text, moderation decisions, and structured data (e.g. story schemas, character models). It sits at the core of the Tomale content pipeline, with all requests orchestrated through Xano using predefined prompt templates and output schemas.

## Key endpoints / schema highlights

- Core use cases:
  - Story generation → structured JSON (pages, text, metadata)
  - Moderation → enforcement decision (`PASS`, `PARENTAL_OVERSIGHT`, `FAIL`)
  - Prompt compilation → transforms user input into structured prompts
  - Character modelling → JSON-based character definitions
- Data model integration:
  - `data_models` table defines:
    - prompt templates
    - output schemas
    - model settings
  - Responses mapped directly into:
    - `instant_story_pages`
    - `instant_stories`
    - `characters`
- Pipeline flow:
  - Input → moderation → text generation → structured response → DB write
- Strict requirement:
  - JSON schema enforcement (no free-form text responses in production flows)

## Version / environment

- OpenAI API (Responses API)
- Model: GPT-4o (and GPT-4o-mini for lighter tasks like moderation/prompting)
- Config driven via:
  - `data_models.model_settings`
- Environment variables:
  - API keys stored in Xano
- Token + cost tracking:
  - Logged in `token_usage` table

## Known gotchas

- JSON output can break if schema is too complex or prompts are not tightly controlled.
- Model behaviour can drift — outputs are not perfectly deterministic.
- Cost scales with usage quickly (token + volume driven).
- Requires retry + validation logic to be production-safe.
- Prompt quality directly impacts output quality — no safety net.
