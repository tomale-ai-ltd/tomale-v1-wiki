# Zustand

## How we use it

We use Zustand as the app-level state layer, with a split between persisted auth state and lightweight entity caches.

**Actual usage today (in code):**
- `useAuthStore` is actively used for auth token/user session state and hydration-gated app bootstrap/routing.
- `useCharacterStore` and `useStoryStore` exist with minimal in-memory shape/actions (`set*`, `select*`) as foundation stores.
- Some screen data (e.g. bookshelf in `useBookshelf`) is still managed with local React state, not yet fully moved into Zustand.
- Persistence is currently applied to auth only (plus additional WIP/planned store variants in branch files), with backend remaining source of truth.

**Intended usage (from specs/docs):**
- Zustand is the canonical global state layer for auth, characters, and stories.
- Auth persists across launches via AsyncStorage with hydration guard before route decisions.
- Character/story stores are intended as simple global caches and selection state (no heavy business logic in stores for this slice).

## Key endpoints / schema highlights

- Global stores (implemented + intended):
  - `auth` (implemented): auth token, user id/profile-lite, onboarding state, hydration flags
  - `characters` (implemented scaffold): in-memory character list + selected character
  - `stories` (implemented scaffold): in-memory story list + selected story
  - `reading` (planned, not implemented in current codebase)

- Current sync pattern in implemented auth flow:
  - Login call succeeds → update auth store (`authToken`, `userId`)
  - Follow-up `/auth/me` call determines onboarding routing
  - Rehydrate on app launch → bootstrap `/auth/me` validation → route

- Canonical API/schema alignment source:
  - `api/openapi/xano.yaml`
  - `.specify/memory/data-model.md`

## Version / environment

- Zustand version in repo: `5.0.8` (pinned; not “latest stable” by default wording)
- Runs client-side in the Expo managed app
- Middleware usage:
  - `persist` + `createJSONStorage(AsyncStorage)` for auth
  - Minimal/non-middleware store setup for base character/story stores
- Works alongside:
  - AsyncStorage (rehydration + persistence)
  - Expo Router (route behavior driven by hydrated auth state)

## Known gotchas

- There are currently parallel store patterns/files in branch history (`CharacterStore`/`StoryStore` and `CharactersStore`/`StoriesStore`), so naming/ownership should be consolidated to avoid drift.
- Easy to over-cache and blur source-of-truth boundaries; Xano should remain authoritative.
- Persistence must be explicitly configured per store and carefully partialized (to avoid persisting unnecessary/sensitive data).
- Store actions are intentionally thin in this slice; data-fetch side effects are still split across hooks/components.
- Zustand debugging ergonomics are lighter than Redux-style tooling unless additional instrumentation is added.
