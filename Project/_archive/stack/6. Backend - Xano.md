# Xano

## How we use it

Xano is the backend system of record for this app’s domain data and auth contracts, and is integrated via a generated OpenAPI client (`api/openapi/xano.yaml` → `api/client.ts`).

**Actual usage in current app code:**

- Auth flows are actively used (`/auth/login`, `/auth/me`).
- Story listing is used in UI via `/instant_stories` (`useBookshelf`).
- Client runtime base URL is configurable via `EXPO_PUBLIC_API_BASE_URL`, with a fallback to a Xano cloud endpoint.

**Intended architecture (documented in specs/data model):**

- Xano owns broader domain + pipeline concerns (stories, pages, characters, jobs, orders, subscriptions).
- Async processing patterns are expected (job tables + executor-style tracking in data model).

## Key endpoints / schema highlights

Core entities clearly present in `.specify/memory/data-model.md`:
- `instant_stories`, `instant_story_pages`, `characters`
- `image_jobs`, `pdf_jobs`, `executor_runs`
- `store_orders`, `subscriptions

OpenAPI contract includes auth and domain endpoints such as:
- `/auth/login`, `/auth/me`, `/auth/refresh`, `/auth/signup`
- `/instant_stories`, `/characters`, `/orders`, `/products`, `/stripe_webhook`

Important caveat:

The exported OpenAPI currently exposes many generic CRUD-style endpoints marked `"Authentication: not required"` in the spec excerpt, so security/ownership guarantees are **not inferable from this repo alone**.

Core pipeline:
  - Story creation → `generate_story_page_text` (GSPT)
  - Image orchestration → `orchestrator_story_images`
  - Workers → `image_worker_tick`, `pdf_worker_tick`
  - Executors → cover/page/character image + PDF generation
  - Order fulfilment → Stripe webhook → PDF → print provider

API design principles (enforced):
  - Auth required by default
  - Ownership filtering: `owner_user_id = auth.user.id`
  - No generic CRUD exposure — endpoints are task-specific
  - Internal functions used instead of exposing system tables

## Version / environment

- Xano (cloud, serverless deployment)
- Separate environments:
  - `dev` → testing + iteration
  - `prod` → live app
- Environment variables used for:
  - API keys (OpenAI, Stripe, SendGrid)
  - Internal worker keys
- Scheduled tasks (cron) for:
  - worker ticks
  - retries
  - reconciliation processes

## Known gotchas

- Easy to accidentally expose data if ownership filtering is missed (critical risk).
- Function stacks can become complex and hard to debug at scale.
- Long-running processes (image/PDF generation) can hit execution limits if not offloaded properly.
- Async job design must be correct (locking, retries, idempotency) or things silently break.
- Observability is limited unless explicitly built (logging, executor_runs, etc.).
