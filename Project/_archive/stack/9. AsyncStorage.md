# AsyncStorage

## Actual vs. intended usage

### Actual (evidenced in code)

- AsyncStorage is actively used as the persistence backend for Zustand via `createJSONStorage`.
- `auth` persistence is implemented in `useAuthStore`:
  - Persists minimal auth state (`authToken`, `userId`) under key `auth`.
  - Hydration flags (`hasHydrated` / `isHydrated`) gate startup flow.
  - Rehydration failure fallback is implemented (clear auth + mark hydrated so app can continue).
- Debug/dev helpers include direct AsyncStorage operations for testing corrupted storage scenarios.
- Additional persisted stores (`CharactersStore`, `StoriesStore`) exist in the branch, but current app flow still primarily relies on auth persistence as the stable path.

### Intended (from docs/specs)

- AsyncStorage is the standard persistence layer for lightweight client state in this architecture.
- Zustand slices persist selectively (not blanket persistence), with hydration-safe routing behavior.
- Token/session continuity across app relaunches is required.
- Security hardening (e.g. moving sensitive token storage to SecureStore/Keychain) is acknowledged as a future hardening decision, not current default.

## Key endpoints / schema highlights

- This layer has no backend endpoints itself; it supports auth/network flow by persisting client state.
- Current storage pattern:
  - Login/auth success -> store token/user identifiers via persisted Zustand state
  - App launch -> hydrate store before route decisions
  - Logout/error fallback -> clear auth state
- Works alongside:
  - Zustand (`persist` middleware)
  - Auth flow/bootstrap logic
  - HTTP client auth header behavior (token read from state)

## Version / environment

- Package: `@react-native-async-storage/async-storage` (`2.2.0` in `package.json`)
- Runtime: local device storage (iOS/Android, Expo managed app)
- No dev/prod separation at storage layer (device-local only)
- Persistence scope is defined by store `partialize` rules (currently minimal for auth)

## Known gotchas

- AsyncStorage is not a secure secret vault; treat persisted auth data as a trade-off, and keep payload minimal.
- Hydration timing matters: route decisions must wait for hydration completion.
- Corrupted storage can create bad startup state unless explicit fallback logic exists (implemented for auth).
- Store proliferation can create inconsistent persistence behavior unless ownership/conventions stay strict.
