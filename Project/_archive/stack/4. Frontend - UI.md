# NativeBase


## How we use it

We use NativeBase as the primary UI component library to rapidly build consistent, cross-platform interfaces across the app (forms, layouts, buttons, modals, overlays). It acts as the foundation layer for most screens, with custom components layered on top for more complex experiences like chat, e-reader, and carousels.

## Key endpoints / schema highlights

- Used across all core screens:
  - Chatbot interfaces (story + character creation)
  - Store checkout flow (forms, inputs, buttons)
  - Characters + Bookshelf screens (layout + structure)
- Provides base components:
  - Layout: `Box`, `VStack`, `HStack`
  - Inputs: `Input`, `TextArea`
  - Actions: `Button`, `IconButton`
  - Feedback: `Modal`, `Toast`, `Spinner`
- Combined with custom components for:
  - Chat UI (message bubbles, suggestion cards)
  - Reader overlays (controls, progress UI)
  - Animated experiences (paired with Reanimated)

## Version / environment

- NativeBase (latest stable compatible with Expo)
- Runs within Expo managed workflow
- Theming configured globally (single source of truth for colours, typography, spacing)
- Works alongside:
  - Zustand (state-driven UI updates)
  - Expo APIs (modals, overlays, device features)

## Known gotchas

- Not all components feel truly “native” — some UI can feel slightly off compared to fully custom builds.
- Theming can become messy if not centrally controlled (easy to override inconsistently).
- Performance can degrade if overused in highly animated screens (e.g. avoid wrapping everything in NativeBase components inside heavy animations).
- You’ll still need custom components for anything differentiated (chat UI, reader, carousel) — NativeBase doesn’t solve those.
