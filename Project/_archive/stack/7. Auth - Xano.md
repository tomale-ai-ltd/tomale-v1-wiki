# # JWT-based auth via Xano  
  
## How we use it  

We use Xano’s built-in JWT authentication to manage user sessions and secure all API access. The frontend stores the token after login and sends it with every request, while all identity and access control is enforced server-side using `auth.user.id`.  
  
## Key endpoints / schema highlights  

- Auth endpoints (public):  
- `/auth/login`  
- `/auth/signup`  
- `/auth/request_otp` (if used)  
- Protected endpoints:  
- All user data routes require valid JWT  
- Identity model:  
- No `user_id` passed from frontend  
- All queries derive identity from:  
- `auth.user.id`  
- Authorization pattern (critical):  
- `WHERE owner_user_id = auth.user.id`  

###Future Implementation###

The app will be moving towards an adult and child profile model, where an adult has approval rights over content created. This has not yet been implemented, and is part of the V1 implementation.

- Parent owns all data  
- Child access scoped via profile selection + backend validation  
  
## Version / environment  

- Managed via Xano auth system (JWT tokens)  
- Tokens issued on login and used in all API requests  
- Environment-specific auth configs (dev vs prod)  
- Works alongside:  
- Frontend token storage (AsyncStorage)  
- Backend ownership + access rules  
  
## Known gotchas  

- If you allow `user_id` in inputs anywhere, you’ve broken your entire security model.  
- Missing ownership filters = data leaks across users (high risk).  
- Token handling on frontend must be consistent (lost token = broken session).  
- No fine-grained roles in V1 — everything is owner-based, so logic must stay simple and consistent.
